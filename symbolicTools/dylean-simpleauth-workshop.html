0. Begin with a precise goal

Your job is the same as in LeanDY: define what executions mean, choose an invariant strong enough to express your goal, and prove that every protocol step preserves it. What changes is where each of these lives. In DYLean, executions are the programs you write, run by an attacker who chooses their arguments.

The message flow is the one from the LeanDY SimpleAuth example, plus an explicit key-setup step. DYLean has no global names, so the pre-shared key has to come from somewhere:

StepDYLean functionActionOutput
SetupSharedKey.generate A BGenerate a fresh key SK(A,B); store one copy for A and one for Btwo key states
Initiator AInitiator.start A BGenerate Na; log Start A B Na; remember the runA → B: (A, B, Na)
Responder BResponder.respond A BCheck identities; encrypt a responseB → A: Enc((Na, A), SK(A,B))
Initiator AInitiator.finish ADecrypt; check against the saved runlogs Done A B Na

As in LeanDY, everything is symbolic: Na is a symbolic random value, and encryption builds an idealized term. The example states its security property twice, and proves each version on its own. The first version is LeanDY's statement word for word:

Read it literally. For every trace the attacker can produce (tr.Reachable reachability), if Done a b na is in the trace, then so is Start a b na. The two proofs have the same shape:

  • LeanDY's valid_trace_mem and DYLean's EventLogged_imp_EventInv both retrieve the invariant that the done event had to satisfy when it was logged.
  • That invariant contains the matching start event, and grind finishes.
  • The DYLean proof has one extra first step, apply_Reachable_implies_Invariant. It is there because of the one difference that remains: which traces the theorem talks about. LeanDY assumes Crypto.valid_trace Γ tr, a trace that already satisfies the invariant. DYLean quantifies over reachable traces: those produced by the protocol functions and the network, with arguments chosen by the attacker. The step from “reachable” to “satisfies the invariant” is a library theorem (section 15). In LeanDY it was left to the user.

The second version adds the order: Start was logged in the part of the trace before Done.

Why two versions

Each framework hands you the event's invariant on a different trace, and each theorem states what naturally comes out:

  • LeanDY. valid_trace_mem returns the event's validity on the whole trace tr. Its proof lifts the validity there by monotonicity, starting from the moment the event was logged. At that step the position is forgotten, so “start is somewhere in tr” is what you get.
  • DYLean. EventLoggedAt_imp_EventInv returns the invariant on tr.prefix i, the trace just before the event was logged. The order is still there, so “Start is in the prefix” is what you get. DYLean's own examples state their properties this way, e.g. SignedDH's client_auth.

Both frameworks check every event against the history before it, so LeanDY's invariant contains the order information too: LeanDY's theorem simply doesn't state it. The ordered version is strictly stronger. It rules out a Start that appears only after Done, which the membership version allows on paper. The membership version would follow from it in a few lines, but here it is proved directly, as in LeanDY.

Both are the same modest correspondence property. Neither says that B ran, that B produced the ciphertext, that a completion is unique, or that the protocol ever completes. As in LeanDY, there is no responder event from which such a statement could be built.

Two facts in this port were checked by compilation, not just by reading the source. (1) The session-state invariant alone supplies the matching Start: a diagnostic variant of Initiator.finish that never receives or decrypts anything still passes its proof (section 14). (2) If B's key copy is compromised, the attacker can make A log Done although Responder.respond is never called, and that trace is proven reachable (section 16). Both theorems still hold in both cases.
For your own protocol

Write your target property first. Decide whether you want local start-before-finish, peer participation, agreement on data, injective authentication or secrecy, and under which compromise conditions. In DYLean the compromise exceptions appear explicitly in the theorem statement (see SignedDH's client_auth), so decide which compromises your theorem tolerates.

2. Choose your primitives, and add the missing one

LeanDY gives every protocol the same symbolic algebra 𝐵 α η: a quotient of raw terms by a normalizer, with a distinguished fail value. DYLean builds Bytes à la carte. Each equational theory contributes one or more constructors, a length function, attacker rules and invariants. A protocol states which theories it needs:

Each BytesFunctor.Has X.SubF means “bytes can be built with the constructors of theory X”. Each AttackerKnowledge.Has means “the attacker can use X's operations”. SimpleAuth needs random values (nonces and keys), literals and concatenation (Comparse serializes messages with them), and symmetric encryption.

The missing primitive

DYLean's standard library (DY/EquationalTheory/) has concatenation, literals, hashing, signatures, Diffie-Hellman and two KDFs, but no symmetric encryption. The port therefore adds it in the example folder, the same way Examples/SignedDHKEM/KEM.lean adds a KEM. The library itself is untouched.

symEnc builds the term Enc { key, msg }. symDec is the destructor: it looks inside a ciphertext (view?) and returns the plaintext only if the key matches. The equation symDec k (symEnc k m) = some m and its converse are proved directly, by grind.

There is no fail byte: decryption returns Err Bytes (an Option), and failure is handled by the program, not stored in a term. This is why the LeanDY obligations of the form na ≠ fail have no counterpart here.

Attacker capabilities come with the primitive

In LeanDY the attacker's deduction rules are one fixed relation. In DYLean each theory contributes rules: here, “encrypt anything you know with any key you know” and “decrypt anything you know with any key you know”. Base knowledge (what the attacker reads from the trace) comes from the trace entries: network messages are known, random values are not.

What else a new primitive must provide

SymEnc.lean mirrors DY/EquationalTheory/Sign.lean section by section: (1) constructors and destructor, (2) attacker rules, (3) the bytes invariant of ciphertexts (section 8), (4) Hoare triples so that the step tactic can execute symEnc and symDec (section 11), and (5) SubAttackerKnowledgeTheorem instances proving that each attacker rule turns publishable inputs into publishable outputs. Obligation (5) is what makes a primitive's invariant sound against the attacker: an invariant that is too generous to the attacker fails here.

Encryption is deterministic (no encryption randomness), like LeanDY's symenc. The ciphertext length is the plaintext length plus 16 bytes, but nothing in SimpleAuth depends on it.

For your own protocol

Look in DY/EquationalTheory/ and in the examples before writing a primitive. If you must write one, copy the closest theory: Hash.lean for a single constructor without a destructor, Sign.lean or this SymEnc.lean for a keyed primitive with a destructor. Expect most of your effort to go into the invariant and the attacker-knowledge theorem, not the constructors.

Each message, plaintext and state is an ordinary Lean structure; each event is a constructor of one inductive type.

Wire formats

Comparse formats are built from combinators. .slowString and .slowBytes are length-prefixed, so another field can follow them. .string and .bytes consume the rest of the input and can only come last. The library proves parse (serialize x) = some x and that serialization is injective for every such format.

The IsWellFormed_eq lemma is the one thing you prove per format. A predicate (invariant, publishability, attacker knowledge, …) holds on the serialized message exactly when it holds on its Bytes fields. Participant names are serialized as literals, which are always public, so they drop out. The grind_pattern lines let automation use the lemma.

The LeanDY workshop found, by inspection, a field-order mismatch between what LeanDY's responder encrypted (nonce, identity) and what initiator_check expected (identity, nonce). The LeanDY example in this folder contains the fix (commit dd9753c, LeanDY pull request #2: it now compares (sna, expectedPrincipal)). In this port both sides serialize and parse the same structure ResponsePayload, so they agree on field order by construction. They could still disagree if you accidentally used two different structures. The executable sanity check in section 6 would then fail.
For your own protocol

Give each message, plaintext and state its own structure, even when it has a single field. Put length-prefixed formats first and at most one extensible format last. Copy the IsWellFormed_eq lemma and its two grind_pattern lines for each format. The proofs depend on them.

4. Write each protocol step as a program

A DYLean protocol step is a program in the Traceful monad. Its definition is a function from the current trace to an optional result and a longer trace (Traceful a := ExecTrace → Option a × {trOut // trIn ≤ trOut}). The trace only ever grows: it is append-only. The actions used here are:

  • Random.genRand n appends a random-generation entry and returns a fresh symbolic value. Freshness is by construction: the value is identified by its position in the trace. LeanDY's initiator instead received its nonce n as an argument and did not guarantee freshness.
  • ProtocolEvent.logEvent ev appends an event.
  • PersistentLocalState.storeLocalState p st appends a state owned by p and returns its handle (its position). getLocalState p h reads the state at handle h and fails unless it belongs to p.
  • Network.sendMessage m appends a message and returns its handle. receiveMessage h reads the message at handle h.
  • parse (from Err, lifted into Traceful) and guard c fail the step when parsing fails or c is false.

Compare with LeanDY, where an exchange is a pure function (time, input, state) ↦ Atom {message, state, events, post_events} and the generic transition performs receive, load, log, store and send in a fixed order. In DYLean you write that order yourself. The constraint is the same as LeanDY's “events before state”: Initiator.start logs Start before storing the state, because the state's invariant mentions that event (section 9).

The handles play the role of LeanDY's ChoiceFn. Whoever calls Responder.respond a b keyHandle msgHandle chooses which message and which key state it reads. The caller is the attacker (section 5), so it can deliver any message to any session.

Failure is an abort, not a default value

In LeanDY a failed check returns the default Atom: the transition still sends fail and stores the Null state. In DYLean a failed guard, parse or symDec stops the program. Entries appended before the failure stay in the trace and nothing after it happens. There is no Null state and no fail message.

For your own protocol

Write each role as straight-line code: load states and keys, receive and parse, check with guard, compute, log the events that later states or messages will need, store, send. Return the handles that the next step will need. Keep secrets in states and do not pass them as function arguments: arguments are chosen by the attacker.

5. Decide what the attacker can do

A trace is reachable if it is obtained from the empty trace by repeatedly calling one of the combined functions, with any input. #combine into ReachabilityConfig builds reachability from the list. Network contributes one capability with a precondition: send any bytes the attacker can derive. So the attacker

  • schedules every protocol function with arguments of its choice (participant names, handles), any number of times, in any order;
  • injects any message it can derive from what it has seen;
  • compromises any stored state: PersistentLocalState.compromise logs a compromise event and then publishes the serialized state on the network.

Anything not in the list never happens. The attacker cannot log protocol events, cannot write into a participant's state, and cannot generate random values (it uses literals instead). It can call SharedKey.generate A B several times, so a pair may have several keys. In LeanDY, Sk a b is a single name.

This is the part that the LeanDY workshop listed as missing from LeanDY's SimpleAuth (“the SimpleAuth file itself does not supply a complete runnable network scheduler or an end-to-end reachable-trace theorem”). In DYLean it is part of every protocol specification.

For your own protocol

List every function the attacker may trigger, including state compromise and any key-compromise functions. Leaving a function out weakens the attacker, so your theorem looks stronger than it really is. Give secrets to participants through states created by a setup function that is itself in the list.

6. Check honest execution before interpreting security

A theorem of the form “if Done then Start” is vacuously true if Done can never be logged. DYLean specifications are executable, so you can test them before proving anything. This is what each example's SanityChecks.lean does.

#guard runs the program at compile time on the empty trace. Symbolic bytes are concrete data with decidable equality, so every guard, parse and decryption is actually evaluated. The honest run returns some (): all checks pass and the field orders agree. A rejected forgery

Without the shared key, an attacker who encrypts the expected plaintext under a key it made up is rejected: A's decryption fails and the run returns none. This is one test, not a proof of responder authentication. Section 16 shows what happens once the key leaks.

The LeanDY workshop could not run Lean, so its honest-run concern was an inspection finding. LeanDY now has SimpleAuthDemo.lean, an executable debug run. In DYLean, such checks sit next to the proofs in every example, and the attack scenarios come with reachability proofs, so they are proven to be traces the theorem talks about.
For your own protocol

Before writing invariants, add an honest run that reaches your final event, prove it reachable, and add a few runs that must fail (wrong key, wrong nonce, wrong identity). If an honest run fails, fix the specification first: proofs about a broken specification are proofs about the wrong protocol.

7. Assign labels and usages

A DYLean Label is a monotone predicate isCorrupt on traces: once corrupt, always corrupt. Label.pub is always corrupt and Label.secret never is. l1.canFlow l2 means “whenever l2 becomes corrupt, so does l1”, i.e. data labelled l1 may be given to whoever can read l2. Bytes are Publishable when they satisfy their invariant and their label can flow to pub, that is, when their label is already corrupt.

Labels are not looked up in a global environment. Each random value receives its label and usage when it is generated, as a ghost argument of genRand's specification. These ghost values exist only in the proof trace, never at runtime:

  • The nonce Na is generated with label Label.pub, matching LeanDY's 𝓟ub for Nonce.Nat.
  • SK(A,B) is generated with sharedKeyLabel A B key: it becomes corrupt as soon as A's or B's copy of that key is compromised. Like Sk a b, it is indexed by an ordered pair.
  • Its usage sharedKeyUsage (type "SymKey") says what the key is for. The encryption invariant checks the usage (section 8). HasUsage is deliberately weak once the key is corrupt: at that point the attacker can use it for anything.
LeanDY's SimpleAuth labels Sk as 𝓢ec forever and has no compromise. The literal translation is Label.secret, but a compromisable state may only hold data that its compromise label can know (section 9), and a secret-forever key cannot satisfy that. To mirror LeanDY exactly you would use Label.secret together with non-compromisable states (PersistentLocalState.State instead of CompromisableState). The port follows DYLean's convention instead: everything stored can be compromised. The authentication theorem is unaffected either way, since it never uses the key.
For your own protocol

For every secret, decide at generation time who may learn it and under which corruption, and encode that as its label. Choose distinct usages for distinct purposes, so that a key generated for one purpose cannot satisfy another purpose's predicate.

8. Define what valid ciphertexts mean

This is the invariant every ciphertext in a valid trace satisfies, in the style of DY*'s AEAD invariant. The ciphertext's label is pub: publishing it is fine, provided its invariant holds. The invariant says the ciphertext was produced either

  • honestly: the key has a usage of type "SymKey", the protocol's predicate holds for that usage, and the plaintext is no more secret than the key, so publishing the ciphertext cannot leak the plaintext; or
  • by the attacker: both the key and the plaintext are public.

LeanDY requires the plaintext of an honest ciphertext to be a pair. The port requires it to parse as a ResponsePayload, and the key usage to be SimpleAuth's. As in LeanDY, the predicate says nothing about who encrypted or when. This is why decrypting it cannot tell A anything about B.

Put into the predicate the provenance your theorem needs, for example “an event Respond a b na has been logged”, and keep the attacker alternative (key public) intact. Prove that the predicate is monotone (SymEncPredProof). Here this is trivial because the predicate does not mention the trace.

9. Define state invariants, including compromise

A state invariant invariant me st tr says what holds of state st owned by me. Storing a state requires it, loading a state provides it. invariant_later is monotonicity: the invariant survives trace extension. It is LeanDY's valid_monotone. Both are about one fixed state value as the trace grows.

The initiator's state carries exactly LeanDY's HasValid content: the nonce is valid and public, and Start me b na has been logged. This is the fact the final step will need.

The key state carries the key's label and usage, so that whoever loads it can encrypt or decrypt with known guarantees. It also records that the owner is the initiator or the responder. That conjunct is needed for the extra obligation that compromisable states bring:

  • invariant_implies_KnowableBy: everything in the state must be knowable by the state's compromise label, which becomes corrupt when that particular state is compromised. For a key copy owned by me, compromising it makes sharedKeyLabel initiator responder key corrupt, which requires me to be one of the two parties.
  • For InitiatorState it holds trivially: the nonce is public.
What InitiatorState does not say

As in LeanDY, it does not mention the key, does not record that the nonce was fresh (although it is), and does not assert any responder participation. Nothing prevents Initiator.finish from being called twice with the same state handle, so Done can be logged twice for one Start. The theorem does not claim injectivity.

For your own protocol

For every state, record the evidence a later step needs: labels and usages of stored keys, past events, relations between fields. For compromisable states, check that everything stored is knowable by the state's compromise label. If a value must stay secret even when the state leaks, it does not belong in a compromisable state.

10. Turn your security goal into event invariants

An event invariant is evaluated on the trace just before the event is logged. That is the precondition of logEvent, and afterwards the event is known to be in the trace. Start can be logged at any time. Done a b na requires an earlier Start a b na, which is exactly LeanDY's event_preds for "done".

Two small differences are worth noticing. LeanDY's event_preds matches on a string tag and ends with a wildcard | _ => true, so a newly added tag is unconstrained by default. DYLean's match is exhaustive over a typed event, so adding a constructor forces you to write its invariant. And because there is no fail, there is no na ≠ fail conjunct.

For responder authentication, add a responder event and connect the protected response to it through the encryption predicate. Renaming events or strengthening the theorem statement cannot supply evidence that is absent from the invariant. Section 18 sketches the change.

11. Understand the proof contract before using tactics

Proofs work on a proof trace: the execution trace plus ghost information, such as the label and usage of each random value. erase turns it back into an execution trace. The trace invariant is the conjunction of per-entry invariants:

  • every network message is Publishable (see the excerpt below);
  • every stored state satisfies its state invariant;
  • every event satisfies its event invariant on the prefix before it;
  • random entries record their ghost label and usage. Bytes invariants such as the ciphertext invariant are checked wherever bytes appear: in messages, states and events.

hoareTriple f pre post says: from any proof trace that satisfies the invariant and pre, running f on its erasure gives an execution trace that is the erasure of a longer proof trace that satisfies the invariant and post. Every SimpleAuth step is proved with pre and post both True: the content is “the invariant is preserved”. That is LeanDY's valid_exchange.

In LeanDY the obligations are grouped by output field (valid_public_bytes, valid_state, valid_events, valid_post_events, valid_restrictions). In DYLean they arise one per instruction, in program order, as the preconditions of the library's Hoare triples:

The step tactic

step symbolically executes the next instruction. It finds the instruction's Hoare triple by typeclass search, tries to discharge the precondition with grind, introduces the postcondition, and moves on. step by tac uses your tactic for the precondition. step with ⟨ g ⟩ supplies a ghost argument (a label and usage for genRand, a key usage for symEnc/symDec).

After each instruction the trace is longer. step monotonizes the context: it transports every hypothesis about the old trace to the new one, using lemmas tagged grind_later. When it cannot, it stops with “cannot monotonize”. Section 14 shows a case where that happens.

For your own protocol

Before running the tactic, write down for each instruction of your step what its precondition needs, and where that fact comes from (an earlier postcondition, a loaded state invariant, a parsed message). If a stored state needs an event, log the event first. If a message needs a property, establish it before sendMessage.

12. Prove key setup and the first message

Key setup. The ghost argument of genRand fixes the key's label and usage. Storing each copy requires SharedKeyStateInv. After unfolding, grind sees that the owner is one of the two parties and that label and usage are the ones just generated.

First message. The nonce gets Label.pub. Logging Start needs nothing: its invariant is True. Storing the state needs a publishable nonce, which comes from the genRand postcondition, and Start a b na logged, which comes from the logEvent postcondition, transported by monotonization. Sending needs the serialized message to be publishable. By InitMessage.IsWellFormed_eq that is the nonce's publishability, which grind finds without help.

Compare with LeanDY's valid_initiator, which chooses witnesses for event_preds and calls prove_is_public. The same facts appear here in program order instead of grouped by output field.

The @[instance] attribute makes each proven triple available to step, which is how the attacker scenarios and other protocols can reuse it.

For your own protocol

Proof scripts in DYLean usually have one step per instruction, plus a by block where a precondition needs unfolding (typically simp only [PersistentLocalState.LocalStateInv.invariant] then grind). If a step fails, read the precondition it printed. It tells you which instruction's contract you have not met.

13. Prove the responder: establishing the encryption invariant

The interesting step is the encryption. Receiving gives a publishable message, parsing relates it to msg, and loading the key gives SharedKeyStateInv. The precondition of symEnc is then discharged in its honest case:

  • the key has usage sharedKeyUsage, whose type is "SymKey" (from the key state);
  • the plaintext parses as a ResponsePayload (parse (serialize x) = some x), so SimpleAuthSymEncPred holds;
  • the plaintext is no more secret than the key, because it is public and pub flows to every label (canFlowTrans).

The one manual line, have: (serialize …).Publishable tr, gives grind the publishability of the serialized plaintext. SignedDH's responder has the same line with the comment “TODO how to infer this automatically?”. Afterwards, sending is automatic: symEnc's postcondition already says the ciphertext is publishable.

LeanDY's valid_responder is one aesop_type_system call, backed by the helper lemma enc_pub registered in the protocol rule set. Neither framework makes this obligation disappear. It is the place where the response is shown to be a legitimate ciphertext.

For your own protocol

When grind fails on a precondition, add the missing intermediate fact as a have. Common ones are the publishability of a serialized value, the unfolded invariant of a loaded state, and a label-flow step through canFlowTrans.

14. Prove the final step: decryption and monotonization

The final step loads the session state (the split opens the pattern match let ({ b, na }: InitiatorState) ← …), loads the key, receives, decrypts, parses, checks and logs Done.

A monotonization pitfall, and its fix

Without the simp only [PersistentLocalState.LocalStateInv.invariant] at * line, the proof fails at the decryption step with:

cannot monotonize (plaintext✝.label tr).canFlow (keySt✝.key.label tr) tr.erase.

symDec's postcondition mentions keySt.key.label tr. To transport that fact to a longer trace, step needs keySt.key.Invariant tr, because labels are stable only for invariant bytes. That fact exists, but it is buried inside the folded hypothesis LocalStateInv.invariant a keySt tr. Unfolding the state invariants exposes it as its own hypothesis, and from then on monotonization works.

The last step has to prove Done's invariant, Start a b na logged. That fact comes from the session state, not from the decrypted message. This is exactly LeanDY's valid_initiator_check. To make the point concrete, this variant was compiled against the example:

For your own protocol

Audit your theorem by asking: would it still hold if I removed the check that I believe authenticates the peer? In DYLean you can answer by compiling a variant like the one above. If it still holds, either the check is redundant for this goal or the goal is weaker than intended.

15. Close the world and extract the theorem

Each ReachableImpliesInvariant instance packages one step's Hoare triple for the reachability configuration. #combine into ReachabilityTheorem assembles them, together with the library's instance for Network (the attacker sending what it knows). The library then proves, by induction on Trace.Reachable, that every reachable execution trace is the erasure of a proof trace satisfying the invariant.

The Network case is where the attacker-knowledge theorem is used: every byte string the attacker can derive is publishable. That theorem is assembled in Instance.lean from each theory's SubAttackerKnowledgeTheorem, including the two proved in SymEnc.lean. Instance.lean builds the concrete bytes, trace entries and invariants from exactly the components listed in the Has… classes:

With these library lemmas, each security proof (section 0) is five tactic lines. apply_Reachable_implies_Invariant turns the statement about reachable traces into one about proof traces satisfying the invariant. EventLogged_imp_EventInv (for initiator_auth_literal) retrieves the invariant of the Done event on some earlier prefix of the trace. EventLoggedAt_imp_EventInv (section 0, for initiator_auth) retrieves it on the prefix before a given position. simp unfolds that invariant, and grind moves the Start event from the prefix to where the statement needs it. #print axioms shows only propext, Classical.choice and Quot.sound for both theorems.

The short final proof has the same reason as in LeanDY: the local proofs already arranged for the needed evidence to be in the invariant. What DYLean adds is the end-to-end statement. The LeanDY workshop's checklist for connecting local proofs to executions (initial configurations, every honest step, attacker injection and corruption, induction) is done here by the reachability configuration and the library.

16. Probe the property with an attack trace

The attacker compromises B's copy of the key, reads it from the network, waits for A's first message and answers it itself. A decrypts, the checks pass, and A logs Done. Responder.respond is never called. The trace is proven reachable, so both theorems apply to it, and both hold: Start was logged at position 6, before Done at position 10.

Two lessons follow. First, the theorem constrains only A's own history. Second, a responder-authentication theorem in DYLean would have to say “B responded or SK(A,B) was compromised”. The attack shows the second disjunct cannot be dropped. With an uncompromised key, section 6's forged response is rejected, but only a theorem can say that every such attempt fails.

For your own protocol

Write at least one attack scenario per compromise disjunct of your theorem and prove it reachable. If you cannot build a scenario for a disjunct, it may be unnecessary. If a scenario violates the conclusion without using any disjunct, you have found an attack, or a bug in your specification.

Exercise: strengthen the example to show responder participation
  1. Add an event Respond (a b: Participant) (na: Bytes), log it in Responder.respond before encrypting, with invariant True.
  2. Let the key usage carry the pair, e.g. sharedKeyUsage a b with data := some (serialize …), and generate each key with the usage for its pair.
  3. Strengthen SimpleAuthSymEncPred: the usage is sharedKeyUsage i r, the plaintext parses as a payload p with p.a = i, and Respond i r p.na has been logged. The responder establishes this right after logging Respond.
  4. In Initiator.finish, symDec's postcondition now gives “Respond a b na logged, or the key is corrupt”. Make that part of Done's invariant (the corrupt case becomes “some copy of SK(a,b) was compromised”).
  5. State the theorem: Done a b na at t implies Respond a b na or a compromise of SK(a,b) before t. Check it against section 16's attack: that trace must fall in the second disjunct.

This is a design sketch. It has not been implemented or compiled as part of this example.

Exercise: distinguish three claims about the same nonce

na.Invariant tr is a symbolic well-formedness fact (here: Na is a genuine random value of the trace). na.Publishable tr concerns confidentiality. “Na was generated at position i” is a trace fact that neither of them records. None of them implies that a session completes at most once.
