Pinned in Place

The KEM reduction replaces the target epoch's key pair and encapsulation by the values a challenger hands it. Stage B proves what the game states reached by such runs look like: the injected values are pinned wherever the state holds them, and the ordinary game invariant still holds. The proof needs no tracking of the transcript across steps, and it holds only on the successors that keep the target unexposed, which is exactly what the stopped run keeps.

01

The reduction exists; now describe its runs

Stage A defined the reduction and showed that the two adjacent hybrids can be stopped when the target epoch is exposed, without changing their difference. The reduction runs the adversary against the injected oracles: the ideal security oracles whose ordinary sends return a fixed key pair at the generation of the target's key epoch and a fixed ciphertext and key at the encapsulation for the target. Everything else is honest.

Stage A, provedCancellation of exposed paths; the reduction, frozen; generic bookkeeping.
Stage B, this pageAn invariant of injected runs on continuing successors; facts about one send and one receive; first-use predicates.
Stages C and DEager equals lazy by three one-use peels; the state map to the reduction; the public theorem.

Stages C and D compare the injected oracles with the honest ones query by query. Every such comparison needs facts about the state at the moment of the query: that the peer key read at the encapsulation site is the injected public key, that the table entry at the target is the injected key, that the retained secret at the target is the injected one. Stage B supplies these facts as an invariant.

02

What the later stages need, and nothing more

The plan's first draft of the invariant quantified over transcript witnesses: for every transcript that witnesses the game invariant, the key pair recorded at the target has the injected public key. Before writing a line, it pays to ask who consumes each clause.

No consumer needs the transcript's ciphertext at the target: both sides of the eventual state map inject the same ciphertext, and the ideal receive ignores it. And no consumer needs the transcript's key pair as such; what matters is the value the peer decodes. So the invariant can be stated entirely on the state. The price is that pinning the decoded value needs an argument, which is the heart of this stage.

03

Preserved on continuing successors only

The stage A review found that the invariant cannot be preserved by every query. The reduction's leaking sends are the honest ones. A leaking send by the owner whose key-generation guard holds at the target's key epoch draws a fresh honest pair, which with positive probability differs from the injected one, and stores its secret at the target. Any clause pinning that secret is violated.

The same send exposes the target. The exposure set of an accepted leaking send is exactly the epochs whose key-generation or encapsulation randomness it leaked, and these are the epochs the two injection tests name. So the violating successor has the target exposed, and the stopped run discards it before the adversary sees anything further.

InjInv(s) ⇒ ∀ z ∈ supp(query from s), t ∉ z.exposed ⇒ InjInv(z) injectedSecurityImpl_preservesInv_continuing, for every selection, every security query, every target t ≥ 1 and supported injected values. The stopping test is applied after the query, so "t unexposed afterwards" is exactly "the stopped run continues".

This is the shape the one-use sampling lemma asks for in its preservation hypothesis, and the shape the stage D state map will carry. A rejected query, whose answer is an ordinary rejection and whose state is unchanged, is a continuing successor and is covered.

The review also warned against a tempting half-measure: keeping the ordinary game invariant unconditional and weakening only the pinning clauses. After an honest leaking generation of the target, a later injected encapsulation would use the injected ciphertext against a different public key, and even the game invariant would fail on that path. The restriction has to apply to the whole invariant.

04 · implemented

The invariant

The target epoch has an owner, the party that generates its key pair: A for even epochs, B for odd ones. The invariant is the ordinary game invariant together with a pinning invariant stated for the owner's state, the peer's state, the peer's outgoing messages and the two key tables.

InjInv t inj s := GameInv s ∧ TargetInv (owner t) t inj own peer peerMsgs ownKey peerKey
The eight clauses of TargetInv
ClauseSaysRole
ek_pinnedWhile the owner's key epoch is t, its retained public key is the injected one.Pins what the peer will decode.
ekPeer_pinnedThe peer's decoded key for t is the injected one.The encapsulation site.
secret_pinnedThe owner's retained secret for t is the injected one.Reserved for stage D.
table_own, table_peerEach table's entry at t is empty or the injected key.The challenge and the ideal receive at t.
ctRec_decodedOnce the owner acknowledges t's ciphertext, the peer has decoded t's key.Three monotone facts recording that the peer decoded the key before any ciphertext for t could exist. They close the hard case of pinning.
ctMsg_decodedOnce the peer recorded a ciphertext chunk for t, it has decoded t's key.
ct_decodedOnce the peer retains a ciphertext at responder epoch t, it has decoded t's key.

Every clause is about the current state. The three decoding clauses look redundant with the protocol's control flow, and in a sense they are: a ciphertext for t can only be produced by an encapsulation, which reads the decoded key. But the ordinary per-party invariant does not record that link, and once the material is gone from the state nothing else does. The clauses carry the link forward, and each is preserved by a local argument because decoded peer keys are never cleared.

05 · the argument

Pinning a key the peer decodes right now

The only clause whose preservation is not a one-line consequence of the step facts is ekPeer_pinned at the peer's receive that decodes the target's public key. The peer assembles chunks, decodes a public key, and stores it as the decoded key for t. Why is it the injected key?

  1. The chunks come from the owner's messages, and the receive-step theorem of the correctness proof says the decoded value is the transcript's public key at t, for the same transcript that witnesses the invariant before and after the step.

    This uses the existing receive step with the ideal recovery function, discharged from the owner's table clause exactly as in the ideal-game invariant.

  2. The owner's key epoch is at least t, because the message that carries chunks for t carries the owner's responder epoch at sending time, which only grows.
  3. If the owner's key epoch equals t: either the owner still retains its public key, which the invariant says is the transcript's key at t and ek_pinned says is the injected one; or it has cleared it, which the invariant allows only after the peer acknowledged decoding, so the peer already had a decoded key for t, contradicting that it is decoding now.
  4. If the owner's key epoch exceeds t: the invariant's secret-key clauses say the transcript's secret at t is retained unless t is acknowledged, and at most one secret is retained, the one for the current key epoch. So t is acknowledged by the owner, and ctRec_decoded says the peer already decoded t's key, again a contradiction.

Step 4 is where the transcript-quantified formulation of the plan breaks down. With the owner past t, nothing in the per-party invariant pins the transcript's key pair at t to anything in the state. The decoding clauses supply the missing fact from the other side: the peer cannot be decoding now because it decoded earlier.

One step at a time, generic in the samplers

The send algorithm is one function, sendWith, parametrised by its key-generation and encapsulation samplers. The honest send, the honest leaking send and the injected send are three instances. Stage B proves the facts about one send step once, for arbitrary samplers:

SendWithFacts role keygen encaps ecCt st key? ρ st' rand
  -- unchanged: requester epoch, decoded peer keys, acknowledgements
  -- with key-generation randomness: a supported pair, public key retained, secret stored
  -- with encapsulation randomness: a supported encapsulation to the decoded peer key,
  --   key emitted at the new responder epoch, ciphertext retained
  -- ciphertext messages carry a chunk of the retained ciphertext

The four preservation lemmas for the pinning invariant are then stated for an arbitrary sendWith output, with hypotheses only at the two hit sites: if this send generates the target's key pair, the pair it generated is the injected one; if it encapsulates for the target, the key it emitted is the injected one. The injected sends discharge both from their samplers. The honest leaking sends discharge both vacuously on continuing successors, because hitting a site exposes the target.

08 · implemented

The game invariant comes for free

The ordinary game invariant was proved for honest sends. The injected send differs only in its samplers, and on an invariant state its samples are honest samples: the injected key pair is in the support of key generation by assumption, and the injected encapsulation is in the support of encapsulation to the injected public key, which is the key the send reads at the target site by ekPeer_pinned.

supp(injectedSend) ⊆ supp(send) on InjInv states injectedSend_support_subset, from sendWith_support_mono: sendWith is monotone in the supports of its samplers, with the encapsulation inclusion required only at the peer key the send actually reads.

So every successor of an injected send is a successor of the honest send from the same state, and the existing preservation theorem applies unchanged. The ideal receives are literally the ideal game's, and the leaking sends are honest, so their game-invariant preservation is reused too.

09 · implemented

First-use predicates for stage C

The eager-sampling stage will draw the target's key pair and encapsulation up front and show this equals drawing them at the query that first uses them. The one-use sampling lemma needs, for each sample, a state predicate "already used" that becomes true at the consuming query, stays true afterwards, and excludes a second consuming query.

Key pair

targetGenerated role t st: the owner's key epoch is at least t. A generating send makes it true; sends and receives keep it; once true, the generation test is false.

Encapsulation

targetEncapsulated t st: the peer's responder epoch passed t, or equals t with a retained ciphertext or an acknowledgement for t. An encapsulating send makes it true; sends and receives keep it; once true, the encapsulation test is false.

These are proved at the level of one send or receive. Lifting them through the game oracles is routine and is left to stage C, which fixes the exact shape of the hit and used predicates the generic lemma takes.

10

What changed from the plan

  • No transcript-quantified clauses. The plan's key_pinned over all witnesses is not derivable from the state once the owner has passed the target. The three decoding clauses replace it, and the plan's fallback of tracking the transcript through the send step was not needed.
  • The ciphertext clause was dropped: nothing in stages C or D reads the ciphertext value.
  • The encapsulation predicate takes no role argument; it describes the encapsulating party's own state.
  • The generic support characterisations of the leaking-send oracles live in the new module rather than in the generic SCKA file, whose imports do not include the game-state update functions.
Check your understanding

Separate the claims

Why is the invariant not preserved by every query?

Because the reduction's leaking sends are honest. A leaking generation of the target's key pair stores a fresh secret, not the injected one. That query exposes the target, and the stopped run discards it, so the theorem only promises the invariant on successors that keep the target unexposed.

Could the proof keep the ordinary game invariant unconditionally and restrict only the pinning clauses?

No. After an honest leaking generation, a later injected encapsulation would pair the injected ciphertext with a public key it was not made for, and the transcript-support clauses of the game invariant would fail. Since the run has stopped, nothing is claimed on that path at all.

Why are decoded peer keys never cleared?

The receive algorithm only adds to the decoded-key map, and the send algorithm does not touch it. This is why the three decoding clauses are monotone and why "the peer already decoded" is a stable fact once established.

Where does the game invariant enter the pinning argument?

In the peer's receive. It supplies the transcript that witnesses the pre- and post-state, the honesty of the owner's message, the clauses tying the owner's retained public key and secrets to the transcript, and the fact that the owner clears its public key only after the peer acknowledged decoding.

Why does the injected send inherit the game invariant rather than needing a new proof?

Its support is included in the honest send's support on invariant states, because its two samples are honest samples at the sites where they are used. Preservation is a property of successors, so it transfers through support inclusion.

Is the retained-secret clause used?

Not by the planned consumers. The stage D state map replaces whatever value sits at the target epoch by the placeholder secret, so it does not need to know the value. The clause is cheap to maintain and kept in case stage D's exact shape wants it.
