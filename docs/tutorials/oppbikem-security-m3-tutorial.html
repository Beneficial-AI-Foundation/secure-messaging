When the Flag Stays Clear

M3a proves that the real security game keeps its consistency invariant whenever its historical KEM-failure flag stays clear. We will build that statement from one query, then extend it to an adversary that chooses queries from earlier answers.

This page covers the completed n4 implementation. M3a supplies the invariant and failure monitor. M3b will bound the probability that the flag is set.

01

What M3a proves

An invariant is a fact preserved through execution. Our invariant, GameInv, describes consistency between the protocol states, their messages and their keys. The proof must cover the security game's leakage, corruption and challenge requests as well as ordinary sends and receives.

Supported security run from the initial state
+ a clear final historical failure flag
⇒ GameInv holds in the final state The theorem assumes deterministic KEM decapsulation and correct erasure codes. It holds for either fixed challenge bit.

A supported outcome is one allowed by the formal computation. The theorem covers every such outcome that meets its flag condition. It does not need a bound on the number of queries.

02

What the invariant says

A transcript records the protocol's sampled KEM values. GameInv requires one transcript that explains both parties' states. Their local records, message tables and key tables satisfy the existing PartyInv conditions against that same transcript.

The original game's correctness flag must also be true. In readable form, the definition is:

GameInv s =
  s.correct = true
  ∧ there exists one transcript T such that
      PartyInv for A holds against T
      ∧ PartyInv for B holds against T

The source contains the full parameters and fields in Correctness/MainInvariant.lean. Consistency against a transcript gives later proofs a link between stored state and sampled cryptographic values. It does not establish that a challenge key looks random.

The definition does not read the exposed or challenged sets. Changing those sets therefore preserves GameInv. This observation supplies the first new theorem:

GameInv kem ecEk ecCt s →
GameInv kem ecEk ecCt
  { s with exposed := exposed, challenged := challenged }

The proof is just the existing proof h. Lean unfolds the definition and sees that the changed fields do not occur. No new transcript argument is necessary.

The exposure guards still decide whether a request is accepted. Bookkeeping independence proves that GameInv survives a bookkeeping update. It does not prove that every guard accepts.

03

What counts as a current KEM failure

A KEM produces a shared key and a ciphertext. Decapsulation recovers a key from a ciphertext with a secret key. Deterministic decapsulation gives one result for a fixed secret key and ciphertext.

The existing kemFailureAt test inspects a party's retained secret key for its peer's current responder epoch. It also inspects the peer's stored ciphertext and key-table entry k. If all three exist, it tests whether decapsulation fails to return some k.

If any component is absent, that party's test returns false. kemFailure runs the test in both directions and combines the results with Boolean OR. The definition lives in Quantitative/Core.lean.

bad(s) := kemFailure hDet s Here, “bad” means this precise state predicate. It is not a test of the adversary's guess.

This test describes the current state. It does not require a receive call to exercise decapsulation at that moment. It can become false later when the relevant retained data changes.

The existing correctness proof supplies a useful local result. If GameInv holds before a query and the current failure test is false, every supported successor satisfies GameInv. M3a extends that result to the full security interface.

GameInv(s) ∧ bad(s) = false
↓ one supported security query
GameInv(s′) The prime means “after the query.” The conclusion allows bad(s′) = true.

That last detail matters. The step theorem proves the invariant in the successor. It supplies no promise that the successor passes the failure test. We need a way to remember when the test first becomes true.

04

Cover every security oracle

An oracle is an operation that the adversary can request. The full security interface adds challenges, corruptions and leaking sends to the correctness interface. M3a handles these operations through the existing shared preservation theorem.

How the one-query proof covers the interface
Oracle familyReason the invariant survives
Ordinary sends, receives and the base sampling queryThe existing correctness step applies under GameInv s and bad(s) = false.
Leaking sends for either partyM1's coin-forgetting identity gives the ordinary send's distribution after the returned coins are removed. Bookkeeping independence handles the exposure-set update.
ChallengeThe key answer depends on the challenge bit. Its state update changes only challenge bookkeeping, which preserves GameInv.
Corruption for either partyRevealing the existing local state changes only exposure bookkeeping in the game state.

The distribution identity for leaking sends also transfers supported outcomes after projection. Revealing coins still changes what the adversary learns. The proof here uses the identity to reason about the successor state.

The handler retains all exposure guards. A rejected request can return none and leave the game state unchanged. That outcome also satisfies the invariant. Sampling effects before rejection remain in the computation.

The shared theorem SCKAScheme.securityImplOf_preserves_at_of_book assembles these facts. The new security_gameInv_step_of_noFailure instantiates it for Opp-BiKEM. M2's concrete exposure package supplies the exposure functions. M3a needs no extra exposure-projection or membership wrappers.

05

Remember the history

A sticky flag stays set once it becomes true. We call it F on this page. The tracked implementation stores the pair (s, F) and starts from (initState, false).

Each query runs the existing security handler. After the handler returns its answer and successor state s′, the monitor applies this rule:

F′ = F ∨ bad(s′) If bad(s′) is false, the flag keeps its old value. If bad(s′) is true, the flag becomes true.

The flag is extra internal state. The oracle interface does not return it to the adversary. The existing generic tracked_run_project theorem says that forgetting the flag gives the original run. M3a reuses that architecture without adding a projection theorem.

There are three separate Boolean values in this discussion:

ValuePurposeInitial value
bThe hidden challenge bit selects real or random challenge answers.Fixed to either value for this theorem.
s.correctThe original game's correctness flag. GameInv requires it to be true.true
FThe monitor remembers whether a post-query state satisfied kemFailure.false

To prove preservation for the tracked implementation, we use a new logical condition on that pair. The generic library calls it trackedInv. We abbreviate it as J here:

J(s, F) := F = true
∨ (GameInv(s) ∧ bad(s) = false)

Read this as two alternatives. Either the flag records a failure, or the state satisfies the invariant and has no current failure. While the flag is clear, the second alternative gives exactly the premises for another use of the local step theorem.

The cases in the generic preservation proof
Before the queryAfter the queryWhy J still holds
F = trueF′ = trueThe flag never clears. The first alternative of J holds.
F = falsebad(s′) = true, so F′ = trueThe first alternative holds. The local step also establishes GameInv(s′).
F = falsebad(s′) = false, so F′ = falseThe local step establishes GameInv(s′). Together with the clear current test, it gives the second alternative.

The flag lets the proof continue after a failure without imposing further conditions on GameInv. A set flag does not say that GameInv is false. It records the point after which this argument no longer guarantees it.

07

From a single step to an adaptive run

An adaptive adversary chooses requests from earlier answers. It can choose a different next query after each answer. A challenge request returns a key response. The adversary can make further allowed requests before it returns its final guess.

A proof for one fixed list of queries cannot cover all of those choices. The local theorem instead quantifies over every security query and every supported answer-state pair. The generic VCVio theorem uses that fact at every branch of the adversary's computation.

  1. Establish the initial condition.

    The existing trackedInv_init gives J(initState, false). The initial state satisfies GameInv and retains no secret key that can trigger kemFailure.

  2. Preserve J for every query.

    The new trackedSecurityImpl_preservesInv applies the generic sticky-flag lemma to the full-security step theorem.

  3. Apply the generic theorem to the whole adversary.

    simulateQ_run_preservesInv gives J in every supported final state. Its proof handles each supported answer and the continuation that the adversary selects from it.

  4. Use the clear final flag.

    If F_final = false, the first alternative of J is impossible. The second supplies GameInv for the final state.

This initialization-and-step pattern is induction. For background, the official Theorem Proving in Lean chapter on induction explains how Lean represents such proofs. The actual simulation induction already exists in the pinned VCVio source.

The new endpoint accepts an arbitrary OracleComp return type. A Boolean adversary guess is one instance. No query-count premise appears in this theorem. The later probability estimate will need one.

Read the nested tuple in the Lean endpoint

The supported outcome is z = (answer, (finalState, finalFlag)). Thus z.2.2 = false means the historical flag is clear, and z.2.1 is the final game state. The theorem concludes GameInv kem ecEk ecCt z.2.1.

The proof first obtains trackedInv from the generic simulation theorem. It splits the two alternatives. The clear-flag premise contradicts the flagged alternative. The other alternative contains the required invariant proof.

08

The five declarations in the implementation

The implementation adds two modules. Their public API contains one abbreviation and four theorems. The project root adds one import of Security.Tracked, which also imports Security.Invariant.

DeclarationPurpose
gameInv_with_security_bookkeepingReplace the exposure and challenge sets while preserving the invariant.
security_gameInv_step_of_noFailurePreserve GameInv across a security query from an invariant state with no current failure.
trackedSecurityImplUse the existing security handler with the generic historical failure monitor.
trackedSecurityImpl_preservesInvPreserve J across every tracked security query.
security_gameInv_of_noFailureConclude GameInv after an adaptive run whose final flag is clear.

Most of the work is composition. The full-security step combines existing oracle lemmas. The tracked preservation proof then supplies that step to the generic helper. Its body is:

trackedImpl_preserves _ _ _
  (security_gameInv_step_of_noFailure kem hDet ecEk ecCt hEk hCt leak b)

The parameters come from the theorem's full signature. hDet is the deterministic-decapsulation assumption. hEk and hCt establish correctness of the two erasure codes. The underscores let Lean infer the handler, failure predicate and invariant.

Open Security/Invariant.lean for the first two declarations. Open Security/Tracked.lean for the monitor and whole-run result. The source statements include all typeclass requirements and parameters.

09

What M3b must add

M3a gives a conditional guarantee on each supported run. To use it in a security bound, we also need an estimate for the runs whose flag becomes set. M3b's target is:

Pr[F_final = true] ≤ q · εcor Planned M3b result. Here q bounds ordinary and leaking sends in total across both parties. ε_cor is the KEM correctness error.

KEM correctness error averages over key generation and encapsulation randomness. A particular key pair can have a much larger conditional error. The proof therefore cannot assume an error bound of ε_cor for every stored key or every current state.

The correctness development already uses an expected score to account for failure risk. M3b must extend the score argument to the full security interface. The existing generic score theorem accepts a tracked-invariant preservation proof, which M3a now supplies.

Available now

The tracked full-security handler, preservation of J, and the clear-flag whole-run endpoint.

Still to prove

The security-query score estimates and the bound on the probability of a set flag. Later game comparisons establish the secrecy bound.

The planned module split places that score work in Security/BadEvent.lean, above the new Security/Tracked.lean. Its exact statements require a separate bounded plan. The existing code assumes neither perfect KEM correctness nor a uniform bound for each key pair.

10

Check your understanding

The current failure test is false at the end. Is that enough to apply the endpoint?

No. The endpoint requires the historical flag to be false. The current state can stop showing an earlier failure. The historical flag remembers it.

The flag becomes true for the first time. Does that mean GameInv is already false?

No. The local step theorem still establishes GameInv in that first successor because its pre-state meets the theorem's premises. The flag removes the guarantee for subsequent steps.

Why does replacing the challenged set preserve the invariant?

GameInv does not read that field. The underlying party states, message tables, key tables and correctness flag remain the same.

Does the bookkeeping theorem imply that a leaking send is always accepted?

No. A guard can reject the request because it conflicts with an earlier challenge. Preservation covers accepted and rejected outcomes.

Is the sticky flag the secret bit that the adversary guesses?

No. The fixed challenge bit b selects the challenge-answer distribution. The historical flag F records a state predicate in the proof monitor. The oracle interface does not return F.

Why does the endpoint need no query bound?

Induction preserves J for any oracle computation represented by OracleComp. Counting sends becomes necessary when we estimate the flag's probability in M3b.
