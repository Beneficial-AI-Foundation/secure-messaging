The Proof So Far

The real security game now has a proved consistency guarantee and a bound on KEM failures. We also have the identity that converts a distance between two game branches into guessing advantage. This page connects those results and explains the work that comes next.

01

The initial foundation is built

Opp-BiKEM sends public keys and ciphertexts in chunks. The parties alternate KEM roles across epochs. An epoch identifies one key-agreement instance. The existing correctness proof explains why these exchanges remain consistent.

The security development adds an adversary that can observe selected send randomness, corrupt party states and request challenge keys. We now know how the real game behaves under all of those requests.

Available nowCorrectness, M1, M2, M3a, M3b and N: real-game consistency, exposure bookkeeping, a failure budget and advantage normalization.
Next constructionsM4, M4′ and M5: an ideal game, its structural invariants, and comparisons with the real game.
Main cryptographic argumentM7, M8, M10 and M11: hybrids, a KEM reduction, adjacent-game bounds and final composition.

The transition toward harder work is real. Most of the completed security steps adapt the correctness machinery. The next phase needs new ideal-game definitions and invariants. Those results are still prerequisites for the main cryptographic reduction.

KEM correctness

Decapsulation recovers the key produced by encapsulation, except with error ε_cor. The current failure bound uses this quantity.

KEM secrecy

An adversary cannot distinguish an encapsulated key from a fresh random key beyond its KEM advantage. The future reduction must connect this property to Opp-BiKEM.

02

What the security experiment asks

An oracle is an operation that the adversary can request. The adversary chooses later requests from earlier answers. This is adaptive interaction. Its eventual Boolean return is its guess of a hidden bit.

The full interface
RequestRole in the experiment
Ordinary send or receiveDrive the protocol and deliver previously generated honest messages. Delivery can involve delay, replay, duplication or reordering.
Leaking sendRun a send and disclose the returned randomness information, subject to the exposure guard.
Corrupt A or BReveal the party's current state, subject to the exposure guard.
Challenge epoch tReturn a recorded key or an independent uniform key, depending on the hidden bit and the eligibility checks.
Base uniform-key queryUse the shared game's key-sampling operation.

The implementation uses b = false for real challenge keys and b = true for random challenge keys. A challenge is an oracle request. The adversary can continue making allowed requests before it returns its final guess.

The game maintains exposed and challenged sets. An exposed epoch cannot become a challenge. A later exposure that conflicts with an earlier challenge is also rejected. These rules protect the meaning of the real-versus-random experiment.

The send budget q counts ordinary and leaking sends across both parties. It applies on every oracle-response path. Rejected send calls count too. Other query types do not consume that send budget.

03

The correctness proof we already had

The correctness game covers ordinary sends, receives and uniform-key queries. Its adversary controls the schedule and delivery of honest messages. The existing theorem bounds failure of the game's correctness assertions.

Pr[correctness game fails] ≤ q · εcor Proved in correctness_failure_le, with deterministic decapsulation, correct erasure codes and at most q ordinary sends.

The proof uses GameInv. An invariant is a fact preserved through execution. Here, the original correctness flag is true, and one common transcript explains both parties' states, message tables and key tables.

It also uses kemFailure, a test for a current KEM inconsistency, and a historical flag F. The monitor sets that flag when a post-query state satisfies the failure test. The flag never clears during a run.

J(s, F) := F = true ∨ (GameInv(s) ∧ kemFailure(s) = false)

This tracked invariant already belonged to the correctness proof. While the flag is false, it supplies the consistency and no-current-failure premises for another step. The correctness development also supplied a score that bounds the flag probability.

The security proof reuses this foundation. It does not assume that the KEM is perfectly correct. A separate existing correctness theorem covers that special case.

04 · implemented

M1: connect ordinary and leaking sends

A leaking send returns extra information about its random choices. The first question is whether the protocol computation still agrees with the ordinary send after that extra output is removed.

Forget the returned coins from a leaking send
= the ordinary send computation

sendWith_rleak_forget proves this identity for either party and every local state. It follows the actual order of key generation, guards, lookups and encapsulation. Sampling that occurs before a later none result remains part of the computation.

The result transfers facts about ordinary sends to leaking sends. It does not claim that disclosing randomness preserves secrecy. The adversary receives extra information, and later arguments must respect that exposure.

M1 also supplies the specialized oracle interface, the Boolean adversary type and SecuritySendQueryBound. Read the M1 tutorial for the shared send engine and its proof.

05 · implemented

M2: define which epochs are excluded

The exposure policy tells the security game which epochs to exclude from challenges after a corruption or a leaking send. It is a conservative rule. Membership in the set alone does not prove that the adversary can reconstruct a key.

For corruption, vuln selects positive epochs whose secret keys remain stored. The new mem_vuln_iff gives that meaning directly. For randomness leakage, rleakEpochs uses the presence of key-generation and encapsulation randomness fields.

M2 proves that those fields agree with the operations of a successful supported send. It identifies the generation and encapsulation epochs, including the epoch advance that key generation can cause.

For every successful supported send:
actual exclusion set = leakEpochs(pre-send state)

This makes the exclusion set predictable from the pre-state. The oracle's acceptance guard still applies. A successful send computation can produce an exposure conflict, in which case the oracle rejects its result and leaves the game state unchanged.

The recent exposure_corrupt and exposure_rleak helpers expose the policy's fields to simplification. The positivity and membership results describe the policy without repeating its filter and image operations. The M2 tutorial gives the detailed epoch calculations.

06 · implemented

M3a: preserve the same invariant in a larger game

Both GameInv and J stay unchanged. The new work proves that the additional security operations preserve them. The correctness theorem alone does not cover those additional query types.

Additional operationNew preservation argument
ChallengeChanging challenge bookkeeping preserves GameInv, which does not read that field.
CorruptionRevealing a local state changes only exposure bookkeeping in the game state. Transcript consistency survives.
Leaking sendM1 transfers the ordinary send's preservation result. Bookkeeping closure handles the exposure update and rejection cases.

The full-security step preserves GameInv from an invariant state with no current failure. The generic monitor then preserves J across every query. Generic induction extends this to arbitrary adaptive oracle computations.

Supported tracked security run from (initState, false)
+ Ffinal = false
⇒ GameInv(sfinal) ∧ kemFailure(sfinal) = false

The stronger endpoint security_noFailure_of_flag_false now retains both facts. The earlier security_gameInv_of_noFailure remains available as its first projection.

For example, corrupting A can reveal secrets while leaving the two party states consistent with the same transcript. This is why the invariant can survive corruption without establishing key secrecy.

The historical flag differs from the hidden challenge bit and the original correctness flag. A current failure test can later become false while the historical flag remains true. The M3a tutorial contains an interactive example.

07 · implemented in the current changes

M3b: bound the historical failure flag

The clear-flag endpoint is useful only if we can also bound how often the flag becomes set. The new security_kemFailure_le supplies that bound for the full security game.

Assume deterministic decapsulation and correct erasure codes. Start from (initState, false). If the adversary makes at most q ordinary or leaking sends, then for either fixed challenge bit:

Pr[Ffinal = true] ≤ q · εcor Here ε_cor := kem.correctnessError ProbCompRuntime.probComp. It averages over key generation and encapsulation randomness.

The theorem uses the same failure predicate, historical flag and score as correctness. Its contribution is extending the expected-score argument to all security queries.

A small average error does not give the same bound for each fixed key pair. For illustration, suppose 1% of generated pairs always fail and the rest never fail. The average error is 1%, but a fixed pair from the first group has error 100%.

The proof records each retained key pair's conditional error in a pending potential V(s). A potential is a quantity used to account for future risk. Here, it sums relevant pending terms for both parties.

Before a failure, the score is that potential. Once the historical flag is set, the score is one:

S(s, F) = if F then 1 else V(s)

The potential can exceed one because it is a sum. It is an accounting quantity, not a probability. When fresh key pairs are generated, their conditional errors average to ε_cor. Later uses of a retained pair carry its already-accounted risk.

The local bound concerns the increase in expected score. It does not assume that every stored key has conditional error at most ε_cor.

The new score step covers every security query
Query or stateAllowed increaseReason
Ordinary sendAt most ε_cor in expectationReuse the correctness score estimate.
Leaking sendAt most ε_cor in expectationM1 transfers the ordinary-send computation. M2 makes the exposure guard state-determined on successful outputs.
Receive or base sampling queryNo increaseReuse the corresponding correctness score estimate.
Challenge or corruptionNo increaseThese operations change only bookkeeping fields, which the failure predicate and score do not read.
Already flaggedNo increase is neededThe flag remains true, and the score remains one.

Rejected leaking sends need care because their send computations sample before the guard runs. The transfer proof retains those samples. If the guard rejects, the state remains unchanged. If it accepts, the marginal identity transfers the ordinary-send bound.

Generic induction now accumulates at most one ε_cor allowance per counted send. The initial score is zero. A flagged final state has score one, so the flag probability is at most the expected final score.

Pr[Ffinal = true] ≤ E[Sfinal] ≤ 0 + q · εcor

The proof permits adaptive choices of later queries. It uses the state-dependent score to keep the average-error argument valid. It adds no stronger assumption about each fixed key.

08 · implemented in the current changes

N: why guessing advantage has a factor of two

The final proof will compare two fixed-bit experiments. The original security experiment instead picks a uniform hidden bit and asks whether the adversary guessed it. Milestone N proves how these quantities relate.

For one fixed adversary, define two probabilities of its final guess being true:

p_real   := Pr[final guess = true | b = false, real keys]
p_random := Pr[final guess = true | b = true, random keys]

In the real branch, the winning guess is false, so the adversary wins with probability 1 − p_real. In the random branch, the winning guess is true, so it wins with probability p_random. Each branch has probability one half.

Pr[Win] = ½(1 − p_real) + ½ p_random
Pr[Win] − ½ = ½(p_random − p_real)

Take absolute values. The distinguishing gap for this adversary is the difference between those two output probabilities. The new sckaDistAdvantage names its absolute value.

Δ = |p_random − p_real|
Advguess = |Pr[Win] − ½| = ½ Δ Proved by sckaGuessAdvantage_eq_sckaDistAdvantage_div_two. This identity does not itself bound Δ.

The shared SCKA proof decomposes the branches and reuses the existing uniform-Boolean lemma. It applies to the general SCKA experiment, beyond this one Opp-BiKEM construction.

Choose hypothetical final-guess rates for the two branches.

Win probability0.75
Distinguishing gap Δ0.50
Guessing advantage ½Δ0.25

These are illustrative probabilities, not measurements from a protocol attacker. Swapping the rates changes the win probability but leaves the absolute advantage unchanged.

Equal branch rates give zero advantage, even if both rates differ from one half. What matters is the change between the real and random experiments.

10 · planned

The next phase needs new mathematical structure

We can reason about the real game and bound KEM failures. To establish secrecy, we must connect real challenge keys to random ones through experiments whose differences we can control.

  1. M4: construct the ideal receive and game.

    Reuse the receive decision tree through a configurable receive function. Prove its real specialization agrees with the current receive. Define the ideal behavior explicitly.

  2. M4′: prove the ideal game's structural facts.

    Establish its invariant, key eligibility and domain facts, the positive epoch bound ≤ 2q, and unique key generation and encapsulation per epoch. These facts cannot be inferred from M3's failure bound. Leakage guards remain in force.

  3. M5: compare real and ideal endpoints.

    Use the failure monitor to bound the difference between corresponding fixed-bit runs. The completed M3 results supply the failure budget and clear-flag consistency facts.

  4. M7: define challenge hybrids.

    A hybrid is an intermediate game in a sequence. Replace challenge behavior epoch by epoch, with exact first and last games.

  5. M8 and M10: build and justify the KEM reduction.

    A reduction turns a protocol attacker into a KEM attacker. It must supply the correct oracle answers around a target epoch, including adaptive exposure and stopping behavior. The proof must relate retained secret state and the candidate session key together. It must also justify sample reordering and the bound between adjacent hybrids.

  6. M11: assemble the final bound.

    Sum the adjacent-game differences, combine the real-to-ideal estimates, and apply the completed normalization identity.

Planned final form:
AdvSCKA(A) ≤ q · εcor + ½ Σt = 02q δt The reductions defining δ_t, the epoch limit and the game-comparison estimates remain proof obligations. This displayed bound is the roadmap target.

The main new difficulty is keeping several executions related while the adversary chooses queries from their answers. The reduction must handle partial messages, retained secrets, candidate keys and exposure at the same time. A generic correctness invariant alone does not establish that relation.

The next concrete implementation target is M4's receive abstraction and ideal-game definitions. M4′ then provides structural facts for the hybrids and reduction. A narrow design check of the joint reduction relation can run alongside that work. This is a direction for later plans, not an implemented theorem.

Check your understanding

Separate the claims

Did M3 add new clauses to the correctness invariant?

No. It preserved the same GameInv and tracked invariant J across the larger security interface. M3b then extended the score estimate to that interface.

Does q · ε_cor already bound the adversary's secrecy advantage?

No. It bounds the historical KEM-failure event. Later game comparisons and the KEM reduction must account for the distinguishing gap between real and random challenge keys.

Why is the pending potential necessary?

Average KEM correctness does not give a uniform error bound for each fixed pair. The potential records conditional risk associated with retained pairs. Fresh sampling supplies the averaging step.

Why must rejected leaking sends still be considered?

The send computation samples before the exposure guard. Its samples remain part of the computation, even when the guard rejects the state update. The send-query budget also counts that call.

What if the hidden bit is true?

This implementation returns random keys on eligible challenges when b = true. The real-key branch uses b = false. The final guess is a separate result of the adversary's program.

Are all prerequisites complete?

The initial real-game foundation and normalization are complete. The ideal-game invariant, epoch bound and uniqueness results remain prerequisites for the main cryptographic argument.
