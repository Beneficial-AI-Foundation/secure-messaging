Two Worlds, One Key

The security proof now has an ideal game in which receivers never decapsulate: they take the key the sender recorded. The real game and the ideal game differ by at most q · εcor, and the ideal game keeps the correctness invariant with no condition at all. This page explains what was built, why the ideal game is unavoidable, and what the small change to the receive proof really is.

Snapshot: 23 October 2026, the unstaged M4/M5/M4′ changes above commit 38416ef. The final key-secrecy theorem remains open; the hybrids and the KEM reduction are the next phase.

01

The first substantive step is built

Up to M3b the security development only ever spoke about the real game: its oracles preserve the correctness invariant while no KEM failure has occurred, and failures happen with probability at most q · εcor. This step introduces a second game and relates the two.

Already availableCorrectness, M1, M2, M3a, M3b and N: real-game consistency, exposure bookkeeping, a failure budget and advantage normalization.
This pageM4, M5 and M4′: an ideal game whose receivers take the sender's recorded key, a real-to-ideal endpoint of q · εcor, the invariant of the ideal game with no condition, and an epoch counter.
Main cryptographic argumentM7, M8, M10 and M11: challenge hybrids, a KEM reduction, adjacent-game bounds and final composition.

Three things changed in the roadmap's cut, all small. M5 was done before M4′ because it needs nothing from the ideal game beyond its definition. The ideal invariant is the existing GameInv, not a weakened copy. And M4′ was trimmed to state-level facts; run-level uniqueness waits for the reduction that will consume it.

02

Why the proof needs an ideal game at all

Start from what a receiver actually computes. When party A receives the ciphertext c for an epoch t whose key pair it generated, it looks up its stored secret key sk for that epoch and sets its session key to

keyA t := decaps(sk, c)

The sender B had earlier run (c, k) ← encaps(pk) and recorded keyB t := k. The game keeps both tables, keyA and keyB, and when the adversary challenges epoch t, the challenge oracle looks up the table entry (A's first, then B's) and either hands out that key or a random one, depending on the bit. Security is about whether the adversary can tell which.

Two things go wrong with decaps(sk, c) for a security proof. They are different problems, and the ideal game solves both with one change.

Problem 1: the two tables can disagree

A KEM with correctness error εcor may decapsulate to the wrong key: with probability about εcor per key pair, decaps(sk, c) ≠ k. When that happens, keyA t and keyB t hold different keys for the same epoch.

This is a nuisance for every statement the hybrid argument wants to make. "The challenge key at epoch t is the key the sender recorded" is false on a failed epoch. "Both parties hold the key that the transcript records" is false. The invariant that pins table entries to the transcript (key_res, key_req) only holds while no failure has occurred, which is why the real-game invariant of M3a carries a no-failure flag. If the hybrids lived in the real game, every one of the 2q + 1 hybrids and the reduction would need that flag, and the failure event would have to be tracked through all of them.

It is cheaper to pay for failures once, up front, and then work in a world where failures do not exist. That is the first job of the ideal game.

Problem 2: the reduction cannot decapsulate at all

This is the fundamental one. Recall what an IND-CPA adversary against the KEM gets: a public key pk*, then a ciphertext c* and a candidate key k*, where k* is either the key encapsulated in c* or an independent random key. It never sees the secret key of pk*.

The reduction for a target epoch t simulates the SCKA game for the adversary and plants the KEM challenge at that epoch: the owner's key generation at t returns pk*, and the peer's encapsulation at t returns (c*, k*). So far everything is computable. Then the adversary delivers c* to the owner, and the simulated receive has to run

keyA t := decaps(sk*, c*)      -- sk* is the one thing the reduction does not have

The reduction is stuck, unless it can answer that receive without sk*. What does it know? It knows k*, the key the simulated sender recorded when it "encapsulated". In the real-key branch of the KEM game, k* is exactly decaps(sk*, c*), up to correctness error. In the random-key branch it is a random key, which is what the hybrid is supposed to hand out at t anyway. In both branches, the rule

receiver's key at t := the key the sender recorded at t

is something the reduction can compute, and the rule decaps(sk*, c*) is not. That rule is the ideal receive. The reduction can only simulate the ideal game, so the hybrid argument has to be carried out in the ideal game.

Read the last column against the KEM bit. If k* is the real encapsulated key, the adversary's view is the ideal game answering the challenge of t with the recorded key. If k* is random, the view is the ideal game answering with a random key. Distinguishing the two hybrids is distinguishing the KEM branches. None of this works in the real column, because the real column's receive needs sk, and in the reduction there is no sk to be had.

Why the ideal game is not cheating

A natural worry: the adversary is supposed to attack the real protocol, and we have just changed the protocol. Two observations settle it.

First, the change is tiny and local. The ideal game runs the same key generations, the same encapsulations, the same erasure-coded messages, the same leaking sends, the same corruptions and the same challenge oracle. Only the one line of the receive that consults the KEM is different. The adversary's view, the messages it sees and the keys it is given, is identical in the two games as long as every decapsulation succeeds, because then decaps(sk, c) = k and the two receive rules return the same value.

Second, decapsulation fails rarely, and the failure is an event of the real game that M3b already bounds: at most q · εcor over a run with at most q sends. So the two games produce the same output except on an event of probability at most q · εcor. That is the M5 endpoint, and it is the only place the KEM's correctness error enters the final bound.

So the ideal game is not a convenience for bounding correctness error. It is the world in which the whole hybrid argument lives, because it is the only world the reduction can simulate. The real game is connected to it by one comparison, paid once.

The resulting shape of the bound is then forced. The adversary's advantage is half the distance between the two real branches. Each real branch is within q · εcor of its ideal branch. What remains is the distance between the two ideal branches, and that distance is what the hybrids and the KEM reduction will bound:

AdvSCKA(A) ≤ q · εcor + ½ · | Pr[Itrue] − Pr[Ifalse] | The first term is Problem 1, paid once. The second term is where Problem 2 is solved, by hybrids whose receives the reduction can simulate.
Could the reduction avoid the ideal game by guessing or by storing the key some other way?

No. Guessing decaps(sk*, c*) is guessing a KEM key, which is the thing the KEM promises is hard. And any rule that produces the right key from the ciphertext without the secret would itself break the KEM. The only key the reduction legitimately holds for c* is k*, and using it at the receive is precisely the ideal rule. There is no other option, which is why every KEM-based reduction of this kind, including the Opp-UniKEM one in this repository, goes through an ideal receive.

Does the adversary notice that receivers no longer decapsulate?

Only through the key it is given at a challenge, and only when decapsulation would have failed. It never sees the receive computation itself; it sees messages and challenge answers. Messages do not depend on the receive rule. Challenge answers agree whenever decaps(sk, c) = k.

03

The recovery function: one knob in the receive algorithm

The receive algorithm does many things: it ingests acknowledgements, advances the requester epoch, buffers chunks, decodes a public key or a ciphertext, and cleans up delivered material. KEM decapsulation happens at exactly one point, in the ciphertext branch:

let sk ← st.req.dk.lookup q        -- the stored secret key for this epoch
let k  ← hDet.decapsDet sk c       -- the only use of the KEM

The new definition recvWith role recover is the same decision tree with that one call replaced by recover q sk c, where

recover : ℤ → SK → C → Option K

takes the epoch, the stored secret key and the decoded ciphertext. The secret-key lookup stays, so a receiver with no stored key fails in both worlds in the same way. Two instances matter.

Real

recover := fun _ sk c => hDet.decapsDet sk c. Then recvWith is definitionally the existing decision tree, and by the existing equivalence lemma it is the production recv. Nothing about the protocol changes.

Ideal

recover := fun q _ _ => peerKey q.toNat, the sender's recorded key for the epoch. The secret key and ciphertext are ignored. This is what "ideal" means here and nowhere else.

Was the receive proof lost? No. The 1200-line invariant proof for receive used its KEM hypothesis exactly once, to rewrite "decapsulate c with sk" into the transcript key. The proof is now stated for recvWith recover with a hypothesis that says the same thing about recover:

hrec : ρ.tRes ∉ stR.ack.ctRec → ∀ pk sk c k,
  (T ρ.tRes).keypair = some (pk, sk) → (T ρ.tRes).enc = some (c, k) →
  recover ρ.tRes sk c = some k

Read it as: at the received epoch, if that epoch is not yet acknowledged and the transcript records key pair (pk, sk) and encapsulation (c, k), then recovery returns k. Two lines of the proof changed: the opening unfold and the one use of the hypothesis. The original lemma, with its original statement and its original KEM hypothesis, is re-derived in one line.

How the hypothesis is discharged in each world
WorldWhat hrec asksWhere it comes from
RealDecapsulating the transcript ciphertext with the transcript secret key gives the transcript key.Decapsulation readiness, exactly as before: from the no-failure flag in the quantitative proof, or from perfect correctness in the perfect-KEM proof. A cryptographic condition.
IdealThe sender's table entry at the epoch is the transcript key.The sender's own invariant clause key_res: at a positive epoch of its responder parity, its table holds the transcript key. No KEM property is used.

A recovery function that returned a wrong key, or failed where the transcript has a key, would violate hrec and the lemma would not apply to it. The hypothesis is the minimal honest requirement at the one point where the receive consults the KEM.

04 · implemented

M4: the ideal oracles and their agreement with the real ones

A receive algorithm cannot see the game's key tables; it only sees the party's local state and the message. The ideal receive oracle therefore reads the game state first and builds the recovery function from it:

oracleRecvAIdeal n := do
  let s ← get
  oracleRecvA (scheme with recvA := recvWith .A (idealRecover s.keyB)) n

B's ideal receive mirrors this with A's table. The ideal correctness oracles are the real sends and uniform sampling with both receives replaced. The ideal security oracles reuse the generic assembly securityImplOf with the same challenge oracle, the same M2 exposure policy and the same leaking sends and corruptions as the real game. Only the two receives differ.

The agreement theorem says that on any state satisfying GameInv with no current KEM failure, every real security query computes exactly what the ideal one computes. For non-receive queries the two handlers are the same term. For a receive, the two recovery functions agree at the one point reached: the invariant pins the decoded ciphertext and the stored secret key to the transcript, the sender's table holds the transcript key, and decapsulation readiness makes the real recovery return that same key.

GameInv(s) ∧ kemFailure(s) = false
⇒ (realImplb t).run s = (idealImplb t).run s

This is a statement about one query from one state. Lifting it to whole runs is the job of M5.

05 · implemented

M5: real and ideal differ by the failure budget

Assume deterministic decapsulation and correct erasure codes, and an adversary making at most q ordinary or leaking sends. For either fixed challenge bit b:

| Pr[Gb outputs true] − Pr[Ib outputs true] | ≤ q · εcor G_b is the real fixed-bit experiment securityExpFixedBit with the M2 exposure package; I_b is idealSecurityExp. Both start from the same initial game state.

The proof is the generic identical-until-bad argument already used for Opp-UniKEM. Both games are run with the same sticky KEM-failure flag. Three facts are supplied about the real tracked run only: it preserves the tracked invariant from M3a, the flag once set stays set, and on states where the invariant holds and the flag is clear, the two handlers agree (the M4 theorem). The generic lemma then bounds the difference of any output event by the probability that the flag is set in the real run, which M3b bounds by q · εcor.

Nothing about the ideal game is assumed here: no invariant, no monotonicity. That is why M5 could be done before M4′.

What the endpoint does not say: it does not say the adversary's advantage is at most q · εcor. The ideal game still answers challenges with real keys when b = false. Secrecy lives in the comparison between the two ideal branches, which is the hybrid argument to come.

06 · implemented

M4′: the ideal game keeps the invariant with no condition

The roadmap expected a weakened invariant for the ideal game, with the correct flag dropped. That turned out to be unnecessary. In the ideal game with correct codes, nothing ever sets correct := false: sends never fail from invariant states, and the generalised receive step proves the four receive-side assertions the oracle checks. So the existing GameInv is preserved as it stands.

PreservesInv (idealSecurityImplb) GameInv No KEM-correctness hypothesis, no no-failure flag. Only correct erasure codes.

Contrast this with the real game, where the same statement holds only from states with no current failure, and only with the historical flag tracking whether that condition has ever broken. The ideal game needs none of that machinery.

07 · implemented

M4′: counting epochs without a ledger

The hybrid argument will index hybrids by epoch and sum over epochs 0 … 2q. For that sum to be complete, no challengeable epoch may exceed 2q. The roadmap once planned a runtime ledger of key-generation slots; it was replaced by a counter that is a pure function of the state:

advances s := ((s.stA.res.resEpoch + 1).toNat + s.stB.res.resEpoch.toNat) / 2

A's responder epoch starts at −1 and B's at 0, and each key-generating send advances one of them by two. So advances is the number of key generations committed so far. Two facts are proved about it.

Per-query step of the counter, on every state (no invariant needed)
QueryChange in advancesReason
Ordinary or leaking sendAt most +1A send moves one responder epoch by 0 or 2; the leaking send reduces to the ordinary one through M1.
Receive, real or ideal0Receive never changes a responder epoch; proved once on recvWith and used for both worlds.
Uniform sampling, challenge, corruptions0They do not touch party states.

The generic state-counter lemma then gives advances ≤ q at the end of any run with at most q sends, in either world. The second fact uses the invariant: on a state satisfying GameInv, every epoch with a recorded key in either table is at most 2 · advances. The argument reads the key off the transcript and uses the invariant's clauses that no key pair or encapsulation exists beyond the owner's current epoch, together with the parity of each party's epochs.

Responder epochs (A, B)3, 4
advances4
Largest possible keyed epoch4

A's responder epoch is −1 + 2a and B's is 2b. A's keys sit at epochs up to 2a, B's up to 2b − 1, so every keyed epoch is at most 2 · (a + b) = 2 · advances, and with at most q sends in total that is at most 2q.

The counter lemmas are stated for the final state of a run. The hybrid argument needs the bound at every point of a run; that follows from the per-query step with a budget-indexed invariant, and belongs to M7 where the exact statement is fixed.

08 · deferred by design

What was not proved here, and why

The roadmap's M4′ also listed run-level history facts: each epoch sees one key generation and at most one encapsulation. These were deliberately left out.

The KEM reduction will embed its single IND-CPA challenge at the target epoch, and it needs to know that the owner's key generation for that epoch and the peer's encapsulation to it each happen at most once. But the precise form of "at most once" depends on the simulation relation the reduction carries: whether it tracks the injection as a phase, as a flag on the state, or as a property of the transcript. Proving a history theorem now would mean guessing that shape.

The state-level ingredients are all in place: responder epochs only grow by the send facts, acknowledgements only grow, a stored ciphertext blocks a second encapsulation at the same epoch, and cleanup only happens after acknowledgement. Assembling them into the right run-level statement is a small task once M8's relation exists.

09

Where this leaves the final bound

AdvSCKA(A) ≤ q · εcor + ½ Σt = 02q δt The first term is now within reach: two applications of the M5 endpoint, one per bit, plus the N normalization. The sum is the hybrid argument.

The guess advantage is half the distance between the two real fixed-bit branches (N). Each real branch is within q · εcor of its ideal branch (M5). What remains is the distance between the two ideal branches, which the hybrids split into 2q + 1 adjacent gaps, each bounded by a KEM reduction's advantage. The ideal invariant (M4′) is what lets every hybrid reuse the same structural facts without re-proving them, and the epoch counter is what makes the sum finite.

Check your understanding

Separate the claims

Does the ideal game assume the KEM is correct?

No. The ideal receive never calls decapsulation. Its invariant holds with no KEM hypothesis at all, which is exactly why it is the right world for the hybrids.

Was the receive-step proof weakened?

No. It was parametrised. The original lemma is re-derived with its original statement and hypothesis. The new hypothesis hrec is the same sentence about an arbitrary recovery function, and both instances discharge it: the real one from decapsulation readiness, the ideal one from the sender's table clause.

Why could M5 be done before the ideal invariant?

The identical-until-bad lemma asks for an invariant and flag monotonicity on the real tracked run only, plus per-query agreement on good states. The ideal handler appears only in the agreement, which is a statement about one query, not about runs.

Does the endpoint bound the adversary's advantage?

No. It bounds the distance between a real branch and the corresponding ideal branch. Secrecy is the distance between the two ideal branches, and that is still open.

Why is the counter defined on every state rather than on reachable ones?

So the generic state-counter lemma applies with no invariant: each query's step bound holds unconditionally. The invariant is needed only once, to turn advances into a bound on keyed epochs.

Could both parties generate a key in the same send?

Not in one send: a send belongs to one party and moves one responder epoch. On unreachable states a single send can both generate and encapsulate, which M2 described honestly; the counter only cares about the responder epoch, which moves by at most two either way.
