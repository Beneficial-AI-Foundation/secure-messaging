Forgetting the Coins

The first Lean result on the road to an Opp-BiKEM security theorem is a small equality: run the leaking send, throw away the coins it reports, and you get the ordinary send. This page explains what that equality says, how it is proved, and why the rest of the plan needs it.

1

The goal: one inequality about an adaptive adversary

Opp-BiKEM is a sparse continuous key agreement (SCKA) scheme. Two parties, A and B, take turns generating KEM key pairs and encapsulating to each other's public keys. Each successful encapsulation defines an epoch key. The security game lets an adversary drive the whole conversation: schedule sends and receives, replay or delay messages, ask for a party's state (corruption), ask a send to reveal its random coins (a leaking send), and challenge any epoch key, receiving either the real key or a uniform one.

The final theorem we are working towards bounds how well such an adversary can tell real keys from random ones:

AdvSCKA(A) ≤ q · εcor + ½ · Σt ∈ range(2q+1) δt q = the adversary's send budget · εcor = the KEM's correctness error · δt = the IND-CPA advantage of an explicit reduction Dt that targets epoch t

Two things make this harder than a textbook KEM proof. The KEM may fail to decapsulate with small probability, so the honest conversation itself can go wrong; that is the q·ε term. And the adversary chooses adaptively which epochs to expose and which to challenge, so no fixed epoch can be singled out in advance; that is why there is one reduction per possible epoch, summed over all of them.

Conventions that matter later. In the SCKA game the challenge bit true means a random key. In the pinned KEM experiment true means the real key. The repository's IND_CPA_Advantage is the full distance between the two KEM branches, and the SCKA guessing advantage is half the distance between the two SCKA branches. That is where the ½ comes from.

The roadmap, and where M1 sits

The plan splits the proof into milestones. Only M1 is implemented. Everything else is a design contract, not Lean.

M1Security interface and the coin-forgetting lemma
M2Concrete exposure policy: which epochs a leaking send or a corruption exposes
M3Real-world invariant through all security oracles; failure budget q·ε
M4Ideal receive built on the existing receive decision tree
M4′Ideal invariant, epoch bound ≤ 2q, one keygen and one encapsulation per epoch
M5Real-to-ideal endpoints: |pb − ib| ≤ q·ε
M7Epoch-indexed challenge hybrids Ht and the key-observation lemma
M8KEM reduction Dt: eager sampling, dummy secret, stop on target exposure
M10Adjacent hybrid gap ≤ δt
NGeneric SCKA normalisation (guess advantage = half the branch distance)
M11Telescoping sum and the final theorem

The dependency order is M1 → M2 → M3/M4 → M4′ → M5 and M7 → M8 → M10 → M11. M1 is upstream of everything: M2 reads the coin record a leaking send returns, M3 and M5 compare leaking and ordinary sends inside the game, and M8's reduction simulates sends on both roles.

Two items that were in the first draft of the plan are gone. A chronological ledger of key-generation slots was replaced by indexing hybrids by epoch number, which needs no extra game state. A pause-and-resume interpreter for the KEM reduction was dropped because the pinned KEM adversary can receive the public key, ciphertext and key all at once and run the whole simulation afterwards.

3

How a send works

Both roles run the same algorithm, sendWith, in SCKA/OppBiKEM/Construction.lean. It is parametrised by two samplers that also return coins: keygen : m ((PK × SK) × RKey) and encaps : PK → m ((C × K) × REnc). The ordinary send instantiates them with the KEM's own operations tagged with the unit coin () and drops the coin record. The leaking sends sendArleak and sendBrleak instantiate them with the leak package's coin-returning versions and keep the record.

Reading the local state st (responder epoch tRes, requester epoch tReq, stored keys, acknowledgements), a send takes these decisions in order:

advance gate
No own public key is stored, and both the responder epoch and its key epoch are acknowledged in ctRec. sample keygen Then tRes := tRes + 2, store the new decapsulation key at epoch tRes + offset, remember the public key, reset the chunk index.
key not yet received?
tRes + offset ∉ ekRec: emit the next erasure-code chunk of the own public key. fails if no key is stored The whole send returns none; on reachable states this cannot happen after the advance gate, because the gate just stored a key.
else: ciphertext not received?
tRes ∉ ctRec. Two sub-cases.
ready to encapsulate
No ciphertext is stored and the peer's key for tRes was decoded (tRes ∈ ekRec). sample encaps to the stored peer key; record the ciphertext and output the epoch key (tRes.toNat, k). fails if no peer key is stored
otherwise
Emit the next chunk of the stored ciphertext, or no payload if none is stored yet.
else
Nothing to send but acknowledgements; the message carries only epochs and flags.

Every path ends by packaging the optional epoch key, the message, the sending epoch, the new state and the coin record { keygenRand, encapsRand }, where each field is some exactly when the corresponding sampler ran.

A detail the proof has to respect. Key generation happens before the possible failure exit. In a general monad an effect that was already performed cannot be deleted just because the continuation returns a constant. So "a failed send returns none" is true for both the leaking and the ordinary send, but both still contain the key-generation bind in front of that none.

4

Coins and marginals: the RandLeak package

The security game has two oracles, sendArleak and sendBrleak, that hand the adversary the randomness a send used. This chapter explains how "the randomness a send used" is even defined, in three steps: the ordinary KEM hides it, a leak package is extra data that exposes it, and two equations are all that tie the package to the KEM.

Step 1 · The ordinary KEM hides its randomness

A KEM in this repository is a monadic program. Key generation has type kem.keygen : m (PK × SK) and encapsulation has type kem.encaps : PK → m (C × K). Each samples internally and returns only its output. Nothing in these types lets a game see what was sampled, so there is no seed to hand out. "The repository does not model randomness as a seed" means exactly this and nothing more.

Step 2 · A leak package is extra data you supply

Because the ordinary program cannot reveal its coins, the game asks for second versions of the two algorithms that can. That is what a value leak : kem.RandLeak is. It bundles four pieces of data and two equations:

structure RandLeak (kem : KEMScheme m K PK SK C) where
  KeygenRand  : Type                              -- the coin type of key generation
  EncapsRand  : Type                              -- the coin type of encapsulation
  keygenRleak : m ((PK × SK) × KeygenRand)        -- key pair, plus a coin value
  encapsRleak : PK → m ((C × K) × EncapsRand)     -- ciphertext and key, plus a coin value
  keygen_fst  : (do let out ← keygenRleak; pure out.1) = kem.keygen
  encaps_fst  : ∀ pk, (do let out ← encapsRleak pk; pure out.1) = kem.encaps pk

The word "coin" is deliberately vague, because the package decides what a coin is. The package is not derived from the KEM; whoever instantiates the security theorem chooses it. Two instances show the range:

The trivial package noLeak

KeygenRand  := Unit
EncapsRand  := Unit
keygenRleak := do
  let out ← kem.keygen
  pure (out, ())
encapsRleak := fun pk => do
  let out ← kem.encaps pk
  pure (out, ())

Every coin is (). Both equations hold by the monad laws alone, since dropping () from (out, ()) gives back out. A leaking send with this package reveals nothing beyond the ordinary send.

A seed-based package

KeygenRand  := Seed
keygenRleak := do
  let r ← sampleSeed
  pure (keysFromSeed r, r)
-- with kem.keygen = do
--   let r ← sampleSeed
--   pure (keysFromSeed r)

The coin is the whole seed, from which the secret key can be recomputed. keygen_fst again holds by the monad laws. A leaking send with this package reveals the secret key of the key pair it generated, and likewise the encapsulated key.

The game cannot tell these two packages apart by their types. Only the two equations constrain a package, and both packages satisfy them.

Step 3 · The two equations are marginal laws

Read keygen_fst as: run the leaking program, keep the first component, throw the coin away. The result must be the ordinary program, as an equality of monadic computations. In a probability monad this says that the distribution of the key pair, with the coin integrated out, is ordinary key generation. That is the marginal distribution of the pair, hence the name. In the free oracle monad used by the games the equality is stronger: the two programs make the same oracle queries in the same order and return the same key pair, with only the extra coin dropped. This is why the M1 theorem can be stated for any lawful monad. Its proof uses nothing but the monad laws and these two equations.

What the laws do not say. They say nothing about the relationship between a coin and the output it came with. A package may return the real seed, a hash of it, or nothing at all. So any theorem that uses only the marginal laws cannot conclude anything about what an adversary learns from the coins. The M1 theorem is such a theorem: it compares two computations after the coins have been removed, so the coins' content never enters.

How M1 lifts the laws to a whole send

The leaking send sendArleak runs the shared engine sendWith with leak.keygenRleak and leak.encapsRleak plugged in. Whenever the engine calls one of them it keeps the coin value, and at the end it returns a record SendRand with two optional fields: the key-generation coin, or none if this send generated no key, and the encapsulation coin, or none if it did not encapsulate. The ordinary send runs the same engine with the ordinary primitives tagged by () and drops the tag at the end. The M1 theorem says that running the leaking engine and dropping the SendRand record gives exactly send. The proof pushes that final projection inward through the engine's binds until it sits directly on a keygenRleak or encapsRleak call, where one of the two marginal laws closes the gap. Chapter 7 walks through it branch by branch.

A forward reference: why M2 treats coins as full exposure

The final security theorem will quantify over every leak package, including the seed-based one above. So the game must assume that a leaking send fully reveals whatever key pair or encapsulated key that send produced. That is why the exposure policy of M2 will mark both coin types as exposing the epoch they belong to. This is a consequence of allowing arbitrary packages, not of the marginal laws, and it plays no role in M1.

5

The four declarations

securitySpec leak Sym

The oracle interface the adversary talks to. It is the generic sckaSecuritySpec (ordinary sends and receives, two leaking sends, challenge, two corruptions) instantiated with Opp-BiKEM's state type, key type, message type and coin record SendRand leak.KeygenRand leak.EncapsRand. An abbrev, so later files see straight through it.

SecurityAdversary leak Sym

A program over that interface returning a Boolean guess. Also an abbrev for the generic SCKAAdversary. Giving it a protocol-specific name keeps later statements readable.

SecuritySendQueryBound adv q

On every oracle-response path, adv makes at most q sends, counting ordinary and leaking sends of both parties together and counting rejected calls. Receives, challenges and corruptions are unbounded. Built on the pinned IsQueryBoundP with the generic send classifier, so no counting machinery is duplicated.

sendWith_rleak_forget

The theorem of this page: for either role and any state, the leaking send with its coin record dropped equals the ordinary send, as a computation in any lawful monad.

All four follow the Opp-UniKEM precedent in SCKA/OppUniKEM/Security/Basic.lean one for one. The only structural difference is that Opp-UniKEM needed two role-specific lemmas because its two parties run different algorithms; Opp-BiKEM's shared engine allows one theorem with a role parameter.

6

The theorem

theorem sendWith_rleak_forget
    {m : Type → Type} [Monad m] [LawfulMonad m]
    (kem : KEMScheme m K PK SK C) (role : Role)
    (ecEk : ErasureCodePayload PK Sym) (ecCt : ErasureCodePayload C Sym)
    (leak : kem.RandLeak) (st : State PK SK C Sym) :
    (do
      let out ← sendWith role leak.keygenRleak leak.encapsRleak ecEk ecCt st
      pure (out.map fun (key, msg, epoch, state, _) => (key, msg, epoch, state))) =
      send role kem ecEk ecCt st

What it says. Take any monad with lawful bind and pure. Run the leaking send and, on success, forget the fifth component of the result. The program you get is literally equal to the ordinary send program. Because the equality is in the monad, it is an equality of distributions once the monad is ProbComp, and it transports every property of ordinary sends to leaking sends: support facts, invariant preservation, expected scores.

What it does not say. It is not a secrecy statement; the coins are still returned to the adversary by the leaking oracle. It is not an oracle-level equality either: the leaking-send oracle in SCKA/Defs.lean samples, then checks that the newly exposed epochs do not intersect the challenged set, and rejects if they do. The theorem is about the algorithm under that guard. It holds on every state, reachable or not, so it needs no invariant, no correctness assumption and no sampling assumption.

7

The proof, branch by branch

The proof has one idea and eleven leaves. The idea: rewrite each ordinary KEM call on the right-hand side as the projection of its leaking version (the marginal laws read right to left), so that both sides sample the same coin-returning program; then show that every continuation projects the same way. Pick a step to see the goal it leaves.

Expanded proof used by the branch explorer 
simp only [send, sendWith, ← leak.keygen_fst, ← leak.encaps_fst, bind_assoc, pure_bind]
split
· simp only [bind_assoc]
  refine bind_congr fun ⟨⟨pk, sk⟩, coins⟩ => ?_
  by_cases hek : st.res.resEpoch + 2 + role.offset ∉ st.ack.ekRec
  · simp only [if_pos hek, pure_bind, Option.map_some]
  · simp only [if_neg hek]
    by_cases hct : st.res.resEpoch + 2 ∉ st.ack.ctRec
    · simp only [if_pos hct]
      by_cases henc : (st.res.ct.isNone && decide (st.res.resEpoch + 2 ∈ st.ack.ekRec)) = true
      · simp only [if_pos henc]
        cases st.res.ekPeer (st.res.resEpoch + 2) with
        | none => simp only [pure_bind, Option.map_none]
        | some peerEk => simp only [bind_assoc, pure_bind, Option.map_some]
      · simp only [if_neg henc, pure_bind, Option.map_some]
    · simp only [if_neg hct, pure_bind, Option.map_some]
· by_cases hek : st.res.resEpoch + role.offset ∉ st.ack.ekRec
  · simp only [if_pos hek]
    cases st.req.ek <;> simp only [pure_bind, Option.map_none, Option.map_some]
  · simp only [if_neg hek]
    by_cases hct : st.res.resEpoch ∉ st.ack.ctRec
    · simp only [if_pos hct]
      by_cases henc : (st.res.ct.isNone && decide (st.res.resEpoch ∈ st.ack.ekRec)) = true
      · simp only [if_pos henc]
        cases st.res.ekPeer st.res.resEpoch with
        | none => simp only [pure_bind, Option.map_none]
        | some peerEk => simp only [bind_assoc, pure_bind, Option.map_some]
      · simp only [if_neg henc, pure_bind, Option.map_some]
    · simp only [if_neg hct, pure_bind, Option.map_some]
The current proof in six lines

The implementation uses split_ifs and split to open the remaining conditions and option matches, then simp to close each branch. The explorer above expands those cases so you can follow them one at a time. The current proof is:

simp only [send, sendWith, ← leak.keygen_fst, ← leak.encaps_fst, bind_assoc, pure_bind]
split
· simp only [bind_assoc]
  refine bind_congr fun _ => ?_
  split_ifs <;> (try split) <;> simp
· split_ifs <;> (try split) <;> simp

Both forms use the same marginal laws and preserve effects before a failed send. The compact form keeps that argument in the Lean source; the expanded form supports the explanation in this tutorial.

What uses it later

MilestoneHow the M1 result is consumed
M2 exposure policyThe coin record's isSome flags say which samplers ran. M2 defines the exposed epochs from those flags and the pre-send state, and proves that on a successful send the flags are determined by the state. The forget lemma shows the state transition is the ordinary one.
M3 real invariant and q·ε budgetInvariant preservation and the per-send expected failure score were proved for ordinary sends in the correctness proof. The forget lemma transfers both to the leaking-send oracle through the generic oracleSendArleak_expectedPayoff_le in SCKA/Security.lean, which asks for exactly this equality.
M5 endpointsThe real-to-ideal comparison uses identical-until-bad over all oracles, including leaking sends. Without M1 each leaking oracle would need its own preservation proof.
M8 reductionThe reduction answers leaking sends by running the leaking engine with the KEM challenge injected at the target epoch. Relating that to the honest hybrid again goes through the marginal laws, now applied at one chosen sample instead of all of them.

The query bound is consumed by M3 (the failure budget is q times the per-send error) and by M4′ (at most q accepted sends means at most q epoch advances, so every keyed epoch is at most 2q, which fixes the hybrid index range).

9

Check yourself

Why is the theorem stated in an arbitrary lawful monad rather than in ProbComp?

Because the proof uses only bind associativity and the unit laws, and because the statement is then usable both for the probabilistic game (ProbComp) and for any simulated or state-threaded version of the send. Nothing about probabilities is needed, so nothing about probabilities is assumed.

Does the theorem show that leaking sends and ordinary sends are interchangeable in the security game?

No. Two things differ at the oracle level: the leaking oracle returns the coins to the adversary, and it rejects a send whose newly exposed epochs intersect the challenged set. The theorem only identifies the underlying algorithms once the coins are discarded.

Where in the proof would a non-lawful monad break things?

At the very first step. Rewriting kem.keygen into keygenRleak >>= fun out => pure out.1 and then pushing the projection through the continuation needs bind_assoc and pure_bind. Without them the two sides are syntactically different programs with no rule to identify them.

Why does the plan call this milestone "no secrecy claim"?

Because every statement in M1 is an interface definition or an algorithmic identity. No probability is bounded, no adversary advantage appears, and no KEM assumption is used. The first probabilistic statement is M3's failure budget; the first use of KEM security is M10.
