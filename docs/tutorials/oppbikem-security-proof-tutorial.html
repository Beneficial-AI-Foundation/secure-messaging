Proving Opp-BiKEM Secure

This chapter tells the complete story of a machine-checked security proof. An adversary plays a game against the Opp-BiKEM key-agreement protocol, corrupting parties, watching coins, and asking to tell a real session key from a random one. We bound its advantage by two quantities it is reasonable to assume small: the correctness error of the underlying KEM and the IND-CPA advantage of one explicit KEM distinguisher built from the adversary. The proof is a chain of games, each hop annotated with its justification. The exposition follows the style of Mike Rosulek's The Joy of Cryptography: security is defined by a library the adversary links to, games are related by small changes whose effect on any caller is understood, and each hop is justified either by a bad event whose probability is paid or by a reduction to an assumption. Every claim here is a theorem in Lean.

Snapshot: 30 October 2026. The proof is complete and every declaration it depends on uses only Lean's standard axioms.

Section 1

Attack scenarios as games the adversary links to

Opp-BiKEM is a continuous key-agreement protocol for two parties, A and B, that talk over a bandwidth-starved channel. Time is divided into epochs. In each epoch one party generates a fresh KEM key pair and sends its public key to the peer, a few erasure-coded chunks per message; the peer, once it has decoded the key, encapsulates a session key against it and sends the ciphertext back, again chunk by chunk; the owner decapsulates. Each party retains only what it still needs: its current secret key until the peer's ciphertext has arrived, its current public key and ciphertext until the peer acknowledges them. Everything else is erased.

The security definition is a library of subroutines with private state, and the adversary is a calling program that links to it and tries to guess a secret bit. The library's state is the two parties' protocol states, two key tables recording the session keys established at each epoch, the messages in transit, and three bookkeeping sets: the exposed epochs, the challenged epochs, and a correctness flag.

The subroutines of the SCKA security library (sckaSecuritySpec)
CallWhat it does
Send-A, Send-BRun the party's send step; put the message in transit; record any new session key in that party's table.
Recv-A n, Recv-B nDeliver the peer's n-th message to the party; record any session key it establishes.
Send-A-rleak, Send-B-rleakAs Send, but also hand the adversary the coins the step used, and expose the epochs those coins belong to. Refused if one of those epochs was already challenged.
Corrupt-A, Corrupt-BHand the adversary the party's whole state, and expose every epoch whose secret key it still retains. Refused if one of those was challenged.
Chall tIf epoch t is neither exposed nor challenged and a key is recorded for it: return that key if the secret bit is 0, a fresh uniform key if it is 1; mark t challenged.
SampleA uniform coin for the adversary's own use.

The adversary may interleave these calls adaptively, observe every answer, and finally output a guess. The library does not let it replace messages, so the network is passive but adaptively scheduled: deliveries may be delayed, reordered or repeated. The exposure rule is the heart of the definition: which epochs become off-limits for challenges after a corruption or a leak. Opp-BiKEM's rule, proved to match what the send algorithm actually does, exposes exactly the epochs of the retained secrets, and, for a leak, the epochs of the key generated and the encapsulation performed by that send.

Remark (one bit, many challenges)

The secret bit is drawn once, before the adversary makes its first call, and it governs every challenge in the run: with bit 0 each eligible challenge returns the recorded key of that epoch, with bit 1 each returns a fresh uniform key. The adversary may challenge as many distinct epochs as it likes, one challenge per epoch, and its single guess is about this global bit. So the question it answers is "are the keys I was shown the real session keys, or random ones?", a multi-instance real-or-random question. There is no per-epoch bit in the definition. Per-epoch selection appears only inside the proof, as the thresholds of the hybrids in Section 5, which answer the epochs below a threshold randomly and the rest honestly; that is a proof device, not part of what the adversary is asked to guess. In Lean this is visible in securityExp, which samples b once and passes it to every challenge through sckaSecurityImpl b.

Definition 1.1 (guess advantage)

The security experiment picks the bit uniformly, runs the adversary against the library, and outputs whether the guess was right. The guess advantage is |Pr[win] − ½|. Writing Pb for the probability that the adversary outputs 1 given that the bit is b, and weighting each bit by its probability ½:

Pr[win]     = ½ · (1 − P₀) + ½ · P₁        -- bit 0 and output 0, or bit 1 and output 1
Pr[win] − ½ = ½ · (P₁ − P₀)

So the guess advantage is half the distinguishing advantage between the two fixed-bit experiments. An adversary that always outputs 1 has P₀ = P₁ = 1, wins with probability ½ and has advantage 0, as it should. The factor of two will follow us to the end.

Section 2

Three ways to justify a hop

Two libraries are shown interchangeable by exhibiting a chain of intermediate libraries, each adjacent pair related by a small change whose effect on any calling program is understood. Our proof is one such chain, and every hop in it is justified by one of three techniques. Everything is concrete: there are no asymptotics and no polynomial-time assumptions, only exact equalities and explicit error terms, because the adversary is an arbitrary computation in VCVio's oracle monad.

Strategy A · The bad-event technique

Two libraries that behave identically until a rare event happens differ, for any caller, by at most the probability of the event. We attach a sticky flag to the real game that is raised the first time a KEM decapsulation returns the wrong key, show that the real and an idealised game agree while the flag is down, and bound the probability that it ever goes up by the number of sends times the KEM's correctness error. This "identical until bad" lemma is formalised once, generically, in the repository's ToVCVio library and reused here.

Strategy B · Hybrids and the chain rule

To get from "all challenges answered honestly" to "all challenges answered randomly", change one epoch at a time. The distance between the endpoints is at most the sum of the adjacent distances, and the sum has a known number of terms because an adversary with q sends can only reach 2q epochs. The endpoints must be identified with the two games we care about; the top one requires a counting argument.

Strategy C · A reduction, by simulation

One hop of the hybrid chain changes the answer at a single epoch from the real session key to a random one. The real session key of an epoch is the key encapsulated in that epoch's ciphertext under that epoch's public key, and the IND-CPA game for the KEM says precisely that such a key, shown next to the public key and the ciphertext, cannot be told apart from a uniform one. So an adversary that notices the hop is a KEM distinguisher in disguise. Making this precise involves three programs.

  1. A is the Opp-BiKEM adversary we are given. We know nothing about it except that it makes at most q sends.
  2. R is the KEM adversary we build, with A as a subroutine. The KEM challenger, which is not ours, draws a key pair (pk, sk) and keeps sk to itself, encapsulates against pk to obtain a ciphertext c and the real key, draws a uniform key, flips a hidden coin, and hands R the triple (pk, c, k*) where k* is the real key or the uniform one according to the coin. The public key is given away because a KEM is a public-key primitive: anyone may encapsulate against it. R does not know which key it received; guessing that coin is its job, and sk is the one thing it never gets.
  3. R runs A and plays the role of A's challenger. It simulates hybrid Ht for a positive target epoch t, with three substitutions and a stopping rule. At the target's key generation, R uses pk and stores a placeholder secret. At encapsulation for t, R uses c and records k* as the session key of t. On an eligible challenge of t, R returns the recorded entry, which is k*. Other calls use the oracles of the ideal game, but a permitted corruption or leaking send that exposes t stops the run with output 0.
  4. If the run continues until A outputs its guess, R outputs the same bit as its guess about the challenger's coin.

Compare the reduction with the stopped hybrids. Let Streal be Ht stopped with output 0 at the first query that exposes t. Define Strandom by stopping Ht+1 under the same rule. With the real candidate key, R outputs 1 with probability Pr[Streal = 1]. With a uniform candidate key, that probability is Pr[Strandom = 1].

Stopping can change each output probability, but it preserves their signed difference. Exposure of t prevents later challenges of t, and an accepted challenge prevents later exposure of t. These two guards ensure that stopping removes equal contributions to acceptance from both hybrids. The reduction's advantage therefore equals the distance between the original hybrids. Section 6 proves this through stopping, drawing the target's values in advance, and mapping the states of the simulation.

The conclusion. If A distinguishes Ht from Ht+1, then R distinguishes a real key from a uniform one in the KEM game. Read in the contrapositive, this is the direction that gives security: a KEM against which no such R has an advantage forces every hop of the chain to be small. In this proof the implication is an equality of numbers:

Adv_IND-CPA(R)  =  | Pr[R outputs 1 | real k*] − Pr[R outputs 1 | uniform k*] |
                =  | Pr[S_t^real = 1] − Pr[S_t^random = 1] |
                =  | Pr[A outputs 1 in H_t] − Pr[A outputs 1 in H_(t+1)] |

so "A distinguishes the hybrids with advantage x" and "R distinguishes real from uniform with advantage x" are the same statement, certified by hybrid_hop_eq_reduction. This is why the final bound contains the advantage of a reduction built from A itself, with no loss. One caution on the word "distinguishes": it means that A's output probabilities in the two hybrids differ by x, not that A knows which hybrid it is in. A plays one game and outputs a bit; the hybrids exist only in the analysis.

Each hop below is annotated with a sentence saying why the change is invisible to the calling program, or what it costs, and with the name of the Lean theorem that certifies it.

Section 3

The theorem

AdvSCKA(A) ≤ q · εcor + q · AdvIND-CPAKEM(B) security, with B := securityReduction … A q. Here εcor is the KEM's correctness error and q bounds ordinary and leaking sends. For a positive budget, B draws one target uniformly from 1, …, 2q and runs that target's reduction. At zero sends, the bound is zero.

The first term pays for KEM correctness failures. The second is the actual IND-CPA advantage of a named adversary. B runs one simulation of A, with one extra target draw. There is no separate premise bounding the advantages of all the target-specific reductions. For a concrete KEM, its security must supply a useful bound on B's advantage.

The proof also gives security_positive, the family bound q · εcor + ½ Σ1 ≤ t ≤ 2q AdvKEM(Rt). security_sum includes the nonnegative target-zero term, while security_uniform gives q · εcor + q · δ when every positive-target reduction has advantage at most δ. These are useful when separate bounds are available for different targets.

Hypotheses of the theorem, and what each one buys

No perfect correctness, no IND-CCA, no bound on the adversary's running time, and no assumption about the reduction's advantage appear. The theorem names the combined reduction; a user instantiating a concrete KEM must bound its advantage.

Section 4

From the real game to an ideal one

The reduction of Section 6 will need to simulate the game without knowing the secret key of the target epoch. But the real receive decapsulates with that secret key. The first move of the proof is therefore to replace the real receive by an ideal one that does not decapsulate at all: when a ciphertext for epoch t is decoded, the ideal receive copies into the receiver's table whatever the peer recorded at t when it encapsulated. This is a standard move: replace a computed value by the "right answer" looked up from a table.

Real receive, at a decoded ciphertext
sk ← dk.lookup t
k  ← decaps sk c
key[me, t] := k
≈q·ε
Ideal receive
sk ← dk.lookup t     -- must exist, value unused
k  := key[peer, t]
key[me, t] := k

The two receives agree exactly when decapsulation returns the key the peer recorded, which is the KEM's correctness event. Strategy A does the rest. The proof shows that the real game keeps a consistency invariant as long as no decapsulation has failed, and that the sticky flag "a failure has happened" is raised with probability at most q · εcor; this uses the invariant to show that every decapsulation in the run is of an honestly produced ciphertext under the matching key, so the average-case correctness error applies. It then concludes, for each fixed bit, that the real and ideal games differ by at most that much.

Three smaller results serve this step. A leaking send, with its reported coins thrown away, is literally the ordinary send, so leaks never change what the parties do. The exposure rule agrees with the operations a send performs. And the ideal game keeps the invariant unconditionally, which every later step relies on; on invariant states, an epoch with a recorded key is at most twice the number of epoch advances, and a run with at most q sends makes at most q advances.

Take-home message

Replace computation by table lookup, pay the correctness error once per opportunity to fail, and never look at a secret key again. From here on, no oracle in the game decapsulates.

Section 5

One epoch at a time

The ideal game with bit 0 answers every challenge with the recorded key; with bit 1, every challenge with a fresh random key. Strategy B bridges them with hybrids indexed by a threshold T: in hybrid HT, challenges at epochs below T are answered randomly and all others honestly. Tables, sends, receives, leaks and corruptions are those of the ideal game, so each hybrid keeps the invariant.

The top endpoint is the subtle one, and it is the reason the bound has 2q terms rather than a number depending on the run. The count works as follows. Each party's epoch counter advances by two per key-generating send, A's keys sit at even epochs and B's at odd ones, so a key can be recorded at epoch e only after e/2 advances, and each send commits at most one advance. The subtlety is that this bound is needed at every query of the run, not only at its end: an adaptive adversary could spend its sends early and challenge a high epoch before the run finishes. The proof therefore carries the remaining send budget in its invariant, advances + remaining ≤ q, which a send keeps because it costs one unit of budget and adds at most one advance, and which no other query touches. So at every query every keyed epoch is at most 2q, below the threshold.

Section 6

One hop is one KEM distinguisher

Fix a target epoch t ≥ 1. The hybrids Ht and Ht+1 differ only at an accepted challenge of t. The first returns the recorded key, and the second returns a random key. Strategy C builds the KEM adversary R of Section 2 from the challenge (pk, c, k*). Its simulation uses pk as the target's public key, c as its ciphertext, and k* as its table entry. It returns A's guess if the run continues, or 0 if a permitted query exposes t.

The real branch must match the acceptance probability of Streal, the stopped version of Ht. The random branch must match that of Strandom, the stopped version of Ht+1. Stopping preserves the signed difference between the original hybrids, which gives the required equality of advantages. Write pT := Pr[HT = 1].

Three things stand in the way, and four steps remove them. The simulator does not know the target's secret key, so it cannot answer a corruption that would reveal it, nor a leak of the target's coins. The honest game draws the target's values when the protocol reaches that epoch, while the simulator holds them from the start. And the simulator's state is not literally the honest state: it stores a placeholder secret and the candidate key. The maneuver that deals with the three is: stop, draw early, rename.

The stop, draw, rename maneuver

If a simulator cannot answer some queries, stop the game there and show that stopping removes equal contributions to acceptance from both games. Draw the target's values early, and show that each change preserves acceptance. Relate the states through a map, compare answers and mapped successors on continuing queries, and compare only the probability mass of stopped queries. Section 7

The final step: one sampled target

The target-specific proofs preserve a signed difference: with pT := Pr[HT = true], Rt's real-minus-random KEM gap is pt − pt+1. The combined adversary B draws t uniformly from 1, …, 2q before the KEM challenge, stores it with the public key, and then runs Rt once. Both KEM branches use the same target distribution.

Pr[Breal = true] − Pr[Brandom = true] = (1 / 2q) Σt=12q (pt − pt+1) = (p1 − p2q+1) / 2q For q > 0, certified by securityReduction_signed_gap_eq. The intermediate terms cancel before the absolute value is taken.

The lower endpoint H1 has the real-key ideal game's acceptance probability, and H2q+1 has the random-key ideal game's. Taking the absolute value turns the preceding identity into |Ideal1 − Ideal0| = 2q · AdvKEM(B).

AdvSCKA(A) = ½ |Real1 − Real0|
≤ q · εcor + ½ |Ideal1 − Ideal0|
= q · εcor + q · AdvIND-CPAKEM(B) The inequality is the real-to-ideal correctness bound. The last equality uses the signed average. At q = 0, the existing family bound has an empty sum and proves the result directly.

Taking the absolute value separately at each target instead gives the family bound from Section 3. That route applies the triangle inequality and loses cancellation between positive and negative gaps. The sampled reduction uses signed telescoping to retain the endpoint difference.

Section 8

What the theorem says, and what it does not

The result is a concrete reduction between explicit games. Its reach is exactly that of the definitions it quantifies over, and three boundaries deserve to be stated plainly.

  • The network is passive. The adversary schedules, delays, reorders and repeats deliveries, but it cannot inject or alter messages. An active attacker is outside the model; the paper's Opp-BiKEM is studied in the same setting.
  • Exposure is the declared policy. After a corruption, the epochs whose secrets the party still retained are off-limits; after a leak, the epochs of the coins leaked. Any claim that some other epoch stays secure after an exposure is not made.
  • The randomness-leak interface is abstract. Only the laws that the leaking algorithms have the honest algorithms as their first component are used. Whether the leaked object lets one reconstruct seeds is a property of the instantiation, not of this theorem.
  • No running-time bookkeeping. The reduction is explicit and computable, and its cost is visibly the adversary's cost plus a simulation of the game, but the theorem states no polynomial-time claim.
  • Average correctness. The correctness error is the average over honestly generated keys and ciphertexts, which is what the game produces; no per-key error bound is assumed.
Take-home message

Everything the adversary can learn about an unexposed epoch's session key, it could have learned from an IND-CPA challenge for that epoch's KEM instance, except for the chance that the protocol itself went wrong. That is the whole content of the theorem, and the proof is a chain of game hops with the three techniques of Section 2.

Exercises

Check your understanding

1. Where does the coefficient q on the combined KEM advantage come from?

The combined KEM advantage is the absolute endpoint hybrid gap divided by 2q. The SCKA guessing advantage pays half the ideal-game branch distance. Thus ½ · 2q = q. The two real-to-ideal error terms are also multiplied by one half, leaving q · εcor.

2. Where would the proof break if the real receive were kept at the target epoch?

In the renaming step. The simulator stores a placeholder secret at the target epoch; a real receive would decapsulate with it and produce a wrong key, and the state map could not relate the two games. The ideal receive looks the secret up only to check it exists, then copies the peer's table entry.

3. Why does the target sampler range over 2q epochs?

The sampler needs a fixed range independent of the run. The epoch bound puts every challengeable epoch in 1, …, 2q on every path with at most q sends. The simulation also handles targets the run never reaches.

4. How does the proof handle a leaking send that exposes the target?

Both hybrids stop with output 0 before the adversary receives the answer. Exposure of the target prevents later challenges of it, and an accepted challenge prevents later exposure. Thus stopping removes equal contributions to acceptance. The simulator therefore need not provide the target's leaked coins. The exposure policy applies without assuming that those coins reconstruct a secret key.

5. Why three applications of the one-use sampling theorem rather than one?

The samples have three distinct query sites and three different "already used" predicates. Each sample is consumed at most once, and the encapsulation depends on the public key drawn by the first. Each application removes one sample while the outer ones are held fixed.

6. ⋆ Could security_uniform be derived from security_sum?

No. The sum in security_sum includes the reduction at target zero, which no hypothesis bounds. The uniform corollary is derived from the positive-target form, which exists because the hop at target zero is exact.

7. Why must the gaps be signed before averaging?

The gap of a mixture is the average of its branch differences, which can have either sign. Taking absolute values first removes the cancellation needed for telescoping. For gaps +0.6 and −0.4, the absolute average is 0.1, while the average absolute gap is 0.5.

8. ⋆ What would change in the proof for an active network adversary?

The invariant that ties table entries to honest transcripts would fail, since a decoded public key might not be the owner's. The reduction's injection relies on the peer encapsulating against the injected public key. A different definition and a different proof would be needed.
