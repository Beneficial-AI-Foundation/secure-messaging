Which Epochs Leak

The second milestone answers a bookkeeping question the security game cannot avoid. When the adversary corrupts a party, or watches the coins of one send, which epochs' keys must be taken off the challenge table? This page explains the rule, shows that it agrees with what the send algorithm actually does, and walks the four Lean proofs.

1

The goal, and the bookkeeping it needs

The target of the whole plan is unchanged from M1: for every adversary that makes at most q sends,

AdvSCKA(𝒜) ≤ q · εcor + ½ · Σt ∈ range(2q+1) δt εcor is the KEM correctness error and δt the IND-CPA distance of the KEM adversary built for epoch t.

The sum over epochs is only meaningful if, for each epoch t, the game refuses to answer a challenge at t once the adversary has learned enough to compute the key at t. The generic SCKA game enforces this with a set Exposed that grows on corruptions and on leaking sends, and a challenge oracle that rejects any epoch in it. What goes into Exposed is protocol-specific. M2 defines it for Opp-BiKEM, and proves that for a leaking send it is a function of the state before the send alone.

That last property is the one later milestones consume. An invariant about the game state can predict what a leaking send will expose before the send runs, so the leakage guard can be reasoned about without re-running the send.

M2 reads the coin record that M1's leaking send returns and turns it into a set of epochs. M3 plugs the resulting package into the game's handlers. M7 and M8 use the membership characterisation to say precisely when their target epoch becomes exposed, which is the moment the KEM reduction must stop.

3

The game's exposure rule

The generic game does not know Opp-BiKEM. It asks the protocol for a package of two functions:

structure VulnerableEpochs (St Rand : Type) where
  corrupt : St → Finset ℕ          -- epochs exposed when this state is revealed
  rleak   : St → Rand → Finset ℕ   -- epochs exposed when a send from this state leaks these coins

Three oracles consume it. The corruption oracle for a party reads corrupt of the party's current state, refuses if any of those epochs has already been challenged, and otherwise adds them to Exposed and hands over the state. The leaking-send oracle runs the leaking send first, and only then checks:

((tIA, IA), ρ, t_snd, stA', rand) ←$ sendArleak(stA)      -- sample first
E ← rleak(stA, rand)                                      -- note: the state BEFORE the send
req E ∩ Challenged = ∅                                    -- otherwise reject, state unchanged
Exposed ← Exposed ∪ E
…

The challenge oracle at epoch t begins with req t ∉ Exposed ∪ Challenged. Three details of this rule shape everything in M2.

  • Pre-state. rleak receives the state the send started from, together with the coins the send returned. A policy written for the post-state would be off by one epoch advance.
  • Failure exposes nothing. If the send returns none, the oracle returns none before computing E. The sampling that happened inside the failed send is still an effect of the computation, which is why M1 insisted on keeping it.
  • Rejection is not failure. A successful send whose exposure collides with a challenged epoch is rejected by the oracle, and the game state is not updated. "The send succeeded" and "the oracle accepted" are different statements, and M2 only ever proves things about the first.
4

What a send does, and when

To know which epochs a send can leak, you need to know which operations it performs and for which epochs. The shared engine sendWith from M1 has two sampling points and this decision structure. tRes is the responder epoch of the pre-state, offset is +1 for A and −1 for B.

gate
Is my own public key absent, and are the ciphertexts at tRes and tRes + offset both acknowledged? keygen If yes, sample a key pair, set tRes := tRes + 2, and store the secret key at epoch tRes + offset, which equals resEpoch + 2 + offset in terms of the pre-state. This is the key-generation epoch.
then
Is my public key for epoch tRes + offset still unacknowledged? chunk ek If yes, emit the next chunk of it. none if there is no key to chunk.
else if
Is the ciphertext at tRes unacknowledged?
and
Is no ciphertext stored, and is the peer's key at tRes acknowledged? encaps Look up the peer key at tRes (none if missing), encapsulate, and emit the key (tRes.toNat, K). This tRes is the one after any advance. This is the encapsulation epoch.
then
Emit the next ciphertext chunk if one is stored. chunk ct
else
Nothing to send but acknowledgement flags. ack only

Two facts fall out of the shape. First, the encapsulation epoch depends on whether the gate fired: it is resEpoch + 2 if a key pair was generated in the same send and resEpoch otherwise. Second, nothing in the engine forbids both samplers from running in one send on an arbitrary state. On reachable states that never happens, but the invariant that says so belongs to M3 and M4′, and M2 does not assume it.

For orientation, the initial states are: A has responder epoch −1 and offset +1, B has responder epoch 0 and offset −1, and both start with the placeholder ciphertexts at −1 and 0 acknowledged. So A's first send generates the key pair for epoch 2 and B's for epoch 1.

5

The policy, line by line

Randomness leakage

def rleakEpochs {RK RE : Type} (role : Role)
    (st : State PK SK C Sym) (rand : SendRand RK RE) : Finset ℕ :=
  let keyEpoch := st.res.resEpoch + 2 + role.offset
  let encEpoch := st.res.resEpoch + if rand.keygenRand.isSome then 2 else 0
  let epochs : Finset ℤ :=
    (if rand.keygenRand.isSome then {keyEpoch} else ∅) ∪
    (if rand.encapsRand.isSome then {encEpoch} else ∅)
  (epochs.filter fun e => 0 < e).image Int.toNat
  • The record decides, not the coins. SendRand has two optional fields. The policy looks only at whether each is some. It never inspects a coin value, so it is the same for every leak package, including noLeak, whose coins are ().
  • Key-generation coin ⇒ the key-generation epoch. With the seed, the adversary can recompute the secret key, hence the session key the peer will later encapsulate to it. That key lives at resEpoch + 2 + offset, exactly where the engine stores the secret key.
  • Encapsulation coin ⇒ the encapsulation epoch. With the seed, the adversary can recompute the encapsulated key. That key is emitted at the advanced responder epoch, so the policy adds 2 precisely when the key-generation field is present.
  • Positive filter, then Int.toNat. Protocol epochs are integers because of the placeholders at −1 and 0, but the game challenges natural numbers and real keys only exist at epochs ≥ 1. Filtering before converting keeps a negative epoch from aliasing epoch 0. This is the same convention as the corruption policy below.

State exposure

def exposure {kem : KEMScheme ProbComp K PK SK C} (role : Role) (leak : kem.RandLeak) :
    SCKAScheme.VulnerableEpochs (State PK SK C Sym) (SendRand leak.KeygenRand leak.EncapsRand) where
  corrupt := vuln
  rleak := rleakEpochs role

vuln already exists from the correctness work: the positive epochs at which the state still stores a decapsulation key. Revealing the state reveals those keys and nothing else of cryptographic value, because stored ciphertexts and public keys are not secrets. This is the paper's retained-key rule. The leak argument fixes the coin types in the package's index so that it unifies with securitySpec leak Sym from M1.

The state-only guards

def sendKeygenGuard (role : Role) (st : State PK SK C Sym) : Bool :=
  st.req.ek.isNone &&
    decide (st.res.resEpoch ∈ st.ack.ctRec ∧ st.res.resEpoch + role.offset ∈ st.ack.ctRec)

def sendEncapsGuard (role : Role) (st : State PK SK C Sym) : Bool :=
  let tRes := st.res.resEpoch + if sendKeygenGuard role st then 2 else 0
  decide (tRes + role.offset ∈ st.ack.ekRec) &&
    decide (tRes ∉ st.ack.ctRec) &&
    st.res.ct.isNone &&
    decide (tRes ∈ st.ack.ekRec)

def leakEpochs (role : Role) (st : State PK SK C Sym) : Finset ℕ :=
  rleakEpochs role st
    ({ keygenRand := if sendKeygenGuard role st then some () else none
       encapsRand := if sendEncapsGuard role st then some () else none } : SendRand Unit Unit)

These read the decision tree off the pre-state. sendKeygenGuard is the gate. sendEncapsGuard is the conjunction of the three conditions on the path to the encapsulation sampler, evaluated at the advanced epoch if the gate fires, and it stops just before the peer-key lookup. leakEpochs feeds unit flags built from the guards into the policy. It is the exposure a successful send will cause, computed before the send runs.

Prediction versus outcome. leakEpochs can be non-empty for a state whose send fails: both guards hold but the peer key is missing from the table. That is not a bug. The theorem in section 7 only equates the prediction with the outcome on successful sends, and the oracle exposes nothing on failure.

The four theorems

mem_rleakEpochs_iff

An epoch t is in rleakEpochs role st rand exactly when t is positive and either the key-generation field is present and t is the key-generation epoch, or the encapsulation field is present and t is the encapsulation epoch (with its conditional +2). This is the interface later milestones use; nobody should unfold rleakEpochs again.

exposure_positive

Both fields of the package contain only positive epochs, for every state and every coin record. A small endpoint, recorded so that no later proof has to re-derive it from the filters.

sendWith_operation_facts

For any samplers and any state, if some (key, msg, epoch, st', rand) is a possible output of the engine, then six things hold: the key-generation field is present iff the keygen guard holds; the encapsulation field is present iff the encapsulation guard holds; the new responder epoch is the old one plus 2 iff a key was generated; if a key was generated, a secret key is stored at the key-generation epoch; the encapsulation field is present iff a session key was emitted; and an emitted key's epoch is the (advanced) responder epoch converted to ℕ.

sendWith_exposure

Under the same success premise, rleakEpochs role st rand = leakEpochs role st. What a successful leaking send exposes is determined by the state it started from. This is the M2 result the plan calls "state-only exposure".

What they do not say

  • Nothing about reachable states. Both samplers may fire in one send on a contrived state, and the theorems describe that honestly rather than excluding it.
  • Nothing about the oracle accepting the send. The oracle's rejection on a challenge collision is a separate condition that M3 will reason about using these theorems.
  • Nothing about what the coins reveal. As in M1, only the presence of a field matters, so the results hold for every leak package.
8

The proofs

Membership: unpacking image and filter

rleakEpochs is an image of a filter of a union of two conditionals. The current proof uses the six-line version suggested in the evaluation. It first rewrites membership in the image, filter and union. In the forward direction, it takes the witness integer e and splits the conditions on the randomness fields. In the backward direction, it supplies t as the witness. simp_all handles the branch facts, and omega handles the Int.toNat arithmetic:

  simp only [rleakEpochs, Finset.mem_image, Finset.mem_filter, Finset.mem_union]
  constructor
  · rintro ⟨e, ⟨he, hpos⟩, rfl⟩
    split_ifs at he <;> simp_all <;> omega
  · rintro ⟨ht, h⟩
    exact ⟨t, ⟨by split_ifs <;> simp_all, by omega⟩, by simp⟩

Operation facts: one walk through the engine

The premise says a particular tuple is in the support of the engine. The support of a bind mx >>= f is the union over samples x of the support of f x, so mem_support_bind_iff turns each sampling point into an existential witness. The proof then runs one loop:

  unfold sendWith at hout
  dsimp only at hout
  repeat' first
    | split at hout
    | (rw [mem_support_bind_iff] at hout; obtain ⟨x, _, hout⟩ := hout)

Each split at hout case-splits the hypothesis on the next if or match in the engine, and each bind is peeled into a witness. When the loop stops, every leaf has the form some (…) ∈ support (pure (…)) or some (…) ∈ support (pure none). One simp only with support_pure turns the first kind into a tuple equality and the second into a contradiction via reduceCtorEq. Substituting the tuple equality makes key, st' and rand concrete in every surviving leaf. From there the key-generation flag equality is proved first and named hkey, because sendEncapsGuard mentions sendKeygenGuard and must be reduced under it; then simp_all closes the six conjuncts in each leaf. The leaves are the same eleven as in M1's branch explorer.

Exposure: four cases and a membership rewrite

  obtain ⟨hkey, henc, _⟩ := sendWith_operation_facts role keygen encaps ecEk ecCt st key msg epoch st' rand hout
  ext t
  by_cases hk : sendKeygenGuard role st <;>
    by_cases hr : sendEncapsGuard role st <;>
    simp [leakEpochs, mem_rleakEpochs_iff, hkey, henc, hk, hr]

This is the payoff of separating the engine analysis from the policy. The two flag equalities are all that is needed. Extensionality reduces the set equality to membership for an arbitrary t, the membership lemma rewrites both sides to the same shape, and the flags on the left are replaced by the guards on the right. Four cases on the two guards finish it. The engine is never unfolded here.

Check yourself

A is at responder epoch 3 with both guards true. What does a successful leaking send expose?

{5, 6}. The key pair is generated for epoch 3 + 2 + 1 = 6 and the encapsulation happens at the advanced epoch 5. Such a state is not reachable, but the policy and theorem cover it.

Why is the policy written for the pre-state rather than the post-state?

Because the oracle calls rleak on the state it read before running the send. Writing it for the post-state would put the key-generation epoch at resEpoch + offset and be wrong by two for every send that advances.

Both guards hold but the peer key is missing. What happens?

The engine samples the key pair, then fails at the peer-key lookup and returns none. leakEpochs is non-empty, but the exposure theorem does not apply, and the oracle exposes nothing. The sampling effect is still part of the computation, which M1's marginal theorem respects.

Does M2 prove that a send never both generates and encapsulates?

No. It proves what is exposed if it does. Mutual exclusion on reachable states is an invariant, and invariants are M3 and M4′ work.

Why does the encapsulation epoch move by 2 when a key pair is generated in the same send?

The engine advances tRes by 2 right after sampling the key pair and only then decides about encapsulation, which uses the advanced tRes for the peer-key lookup and the emitted key. The policy must follow the same order, so it adds 2 exactly when the key-generation field is present.

What does the verdict say about the step?

Accept. Contract match, build, lint, axioms and semantics all check out. The suggested six-line membership proof is now applied. Two helper suggestions are saved for M3: projection lemmas for exposure if later proofs need them, and a membership lemma for vuln. The evaluation also identifies a diagnostic check spent on unsupported tactic syntax; future executors should check syntax in the pinned sources before using it.
