01 / THE CLAIM

Agreement is only the beginning.

A correctness proof says that the parties obtain matching keys and report consistent epochs when they follow the protocol. A security proof says that an observer cannot tell an eligible shared key from a fresh random key, except with a bounded advantage.

Already developed

Correctness

Our repository has Opp-BiKEM invariants and a quantitative correctness bound. Even a KEM that sometimes fails can be handled.

The new goal

Secrecy

We must account for everything the adversary sees, including message timing, public chunks, selected leaked randomness, and allowed state compromises.

A broken construction could always give both parties the all-zero key. It would agree perfectly, but anyone could predict its key. This is why the existing correctness proof cannot by itself settle security.

We aim for a reduction: an explicit algorithm that turns any successful Opp-BiKEM distinguisher into a successful distinguisher against the underlying KEM. The conclusion is conditional on that KEM resisting the constructed algorithms. It does not prove the hardness of the KEM from first principles.

The scope matters. The SCKA game models an observer who can schedule delivery of authentic messages, and can request certain compromises. It does not give the observer arbitrary forged protocol messages. Authentication belongs to the surrounding messaging layer. [SCKA, §3.1]

02 / THE BUILDING BLOCK

A KEM hides one shared key.

A key encapsulation mechanism, or KEM, has three operations. Key generation produces a public key and a secret key. Encapsulation uses the public key to produce a ciphertext and a shared key. Decapsulation uses the secret key and ciphertext to recover that shared key.

KeyGenpublic key pk
secret key sk
→
Encaps(pk)public ciphertext c
shared key k
→
Decaps(sk, c)recover k
or fail

The KEM security experiment asks whether (pk, c, k) can be distinguished from (pk, c, u), where u is independently uniform in the key space. This is the KEM’s IND-CPA notion. The adversary has no secret-key or decapsulation oracle in that experiment.

Opp-BiKEM repeats this pattern. A encapsulates keys for odd epochs; B encapsulates keys for even epochs. At the same time, each party prepares public keys for upcoming epochs. Each local state therefore has both a requester part, which will decapsulate, and a responder part, which encapsulates.

The roles for two adjacent epochs
EpochPublic/secret key ownerEncapsulates and first records kReceives c and erases sk
1, 3, 5, …BAB
2, 4, 6, …ABA

Public keys and ciphertexts travel as erasure-code chunks: several small pieces that the receiver collects and decodes. These pieces add no secrecy. They make scheduling and reconstruction part of the proof. Our protocol also corrects acknowledgement indices in the printed algorithms, so the theorem must refer to the corrected Lean construction. [Construction]

Why two counters instead of one “current epoch”?

A party may be receiving the ciphertext for one epoch while helping send material for another. Its requester and responder counters describe different work. This is also why a send query, a key-generation event, and a completed epoch cannot be counted interchangeably.

03 / THE EXPERIMENT

Give the adversary a precise interface.

A cryptographic game is a program that specifies what an adversary can request and observe. An oracle is one operation exposed by that program. “Adaptive” means that the adversary chooses its next request after seeing previous replies.

OracleWhat the adversary controls or learns
Send A / Send BRequests an honest send and observes the message and epoch metadata. The newly established key is recorded inside the game.
Receive A / Receive BSelects a previously sent peer message by index. This permits delayed, reordered or repeated delivery, subject to the implemented handlers.
Leaking sendRequests a send and its returned randomness. A compatible exposure policy must identify every affected epoch.
Corrupt A / Corrupt BObtains the current local protocol state if doing so does not expose an already challenged epoch.
Challenge(t)For an eligible recorded epoch, obtains either its real key or an independent uniform key, depending on the game’s hidden bit.

Real branch: G₀

Every accepted challenge returns the recorded epoch key. In Lean, the fixed SCKA bit is false.

Random branch: G₁

Every accepted challenge returns a fresh uniform key. In Lean, the fixed SCKA bit is true.

The adversary returns one Boolean. Let p₀ and p₁ be its probabilities of returning true in the two branches. These are output probabilities, not probabilities of winning.

D = |p₁ − p₀|
AdvSCKA = |Pr[correct guess] − ½| = ½ DThe second equality needs the normalization bridge for the actual experiments. Reuse VCVio’s existing uniform-Boolean identity after expressing the SCKA game as its two fixed-bit branches; the SCKA-specific bridge remains to be proved.

The random replacement can happen to equal the real key. That does not invalidate the experiment: indistinguishability compares distributions, rather than demanding that every pair of samples differ.

04 / AN INTERACTIVE EXAMPLE

Erasure helps only if exposure never happened.

An epoch is currently vulnerable when a state compromise now would reveal its retained secret key. An epoch is exposed once an accepted compromise has revealed relevant material. Vulnerability can disappear when a key is erased. Past exposure stays recorded.

Two ordering rules protect the meaning of the challenge. If an epoch was exposed first, its challenge is rejected. If it was challenged first, a later request that would expose it is rejected. A rejected request returns none and does not commit the game-state update.

The concrete exposure policy: mark the generated key’s epoch when a leaking send returns key-generation coins, and the encapsulated epoch when it returns encapsulation coins. Use the old state and actual operation flags; keep only positive epochs. Full encapsulation randomness can reveal a shared key even when the sender stores no secret key, so newly retained secret keys alone are insufficient. A no-leak package may return only Unit; the interface policy conservatively covers the full-randomness model.

In a full run, a corruption is checked against all challenged vulnerable epochs. The explorer projects this check to epoch 1. Source: challenge, corruption and leaking-send handlers; vuln.

First: make agreement automatic.

In the ideal experiment, when a receiver finishes reconstructing an honest ciphertext, it obtains the sender’s recorded key instead of decapsulating. We specialize the existing recvSpec decision tree, retaining its secret-key existence check and advanced requester epoch. The production receive function stays unchanged. Before any KEM correctness failure, real and ideal replies agree; failures of the replacement operation still roll back transactionally.

A bad event records the first KEM correctness failure. We prove that the games behave identically until that event and bound its probability. We do not assume the failure never happens, and we do not condition the experiment on success.

|Pr[Gb = true] − Pr[Ib = true]| ≤ q εcorTarget for each fixed bit b. Here q counts all ordinary and leaking send queries on every response path; εcor is the KEM’s average correctness error.

This is the step already established for Opp-UniKEM by PR #362. Opp-BiKEM needs an adapted proof covering both receive directions. The existing Opp-BiKEM correctness proof supplies much of its invariant and failure-accounting machinery.

Why “at most q failures, each with probability ε” is too quick

The adversary sees public keys and can decide which exchanges to complete. A particular selected key pair may have a larger failure probability than the average KEM error. The current correctness proof tracks a conditional failure “credit” for pending key pairs. Sampling creates credit; completing an exchange spends it. Averaging when the key pair is generated recovers the ordinary KEM error. We will extend that accounting to security queries.

Second: replace eligible challenge keys gradually.

A hybrid argument inserts intermediate games between I₀ and I₁. Each adjacent pair changes the treatment of one target KEM instance. We build a KEM adversary for that one change, then add the resulting bounds.

Index the hybrids by the protocol’s epoch number. In hybrid HT, an eligible challenge for epoch t gets a random answer exactly when t < T. The internal tables still contain their honest keys. Prove that q send queries can create no challengeable epoch above 2q. Then H0 is the real-challenge ideal game and H2q+1 answers every eligible challenge randomly. No extra slot map is needed in the game state.

Third: add the costs.

The triangle inequality adds the two endpoint costs and the middle hybrid costs. Finally, the normalization bridge converts a fixed-branch distance into the repository’s guessing advantage. The numerical result is explained in section 7.

06 / THE KEM REDUCTION

Use KEM security for the middle step.

This section explains the middle arrow from section 5: I₀ → I₁. We replace real challenge answers with random ones, one epoch at a time. KEM security must justify each replacement.

A reduction converts one kind of attacker into another. Here, we build a KEM attacker that runs the SCKA attacker inside a simulated conversation. If the SCKA attacker can notice one replacement, the reduction uses that ability to attack the KEM.

Focus on one epoch.

Suppose epoch 7 has a recorded key k₇. Compare the neighboring hybrid games H₇ and H₈ from section 5. Both use ideal receiving and keep their honest internal keys.

GameAnswer to Challenge(7)Other challenge answers
H₇The actual epoch key k₇Random below epoch 7, real above it
H₈A fresh uniform key, independent of k₇The same rule as H₇

These games differ only in the rule for answering Challenge(7). The attacker receives a key without a label that says “real” or “random.” We must bound its ability to tell which game it is using.

Use the SCKA attacker to solve a KEM puzzle.

There are two experiments here. The KEM challenger supplies a puzzle to our reduction. The reduction supplies a simulated SCKA conversation to the SCKA attacker:

  1. Obtain the KEM puzzle. The reduction receives a public key pk*, a ciphertext c*, and a candidate key k*. The candidate is either the actual encapsulated key or an independent uniform key. The challenger does not reveal which case applies.

  2. Simulate the conversation. The reduction runs the SCKA attacker and answers its oracle queries. It inserts pk* at epoch 7’s public-key generation event. It inserts c* and k* at that epoch’s encapsulation event, and arranges for Challenge(7) to return k*. Other epochs follow the shared rules of H₇ and H₈.

  3. Turn the final answer into a KEM guess. After Challenge(7), the SCKA attacker can make more permitted queries. Eventually, it returns its final Boolean answer. The reduction uses that answer to guess whether the KEM candidate was real or random.

The simulation proof must connect a real KEM candidate to H₇ and a random candidate to H₈. Target exposure paths need the separate cancellation argument below. Once we prove these connections, an attacker that distinguishes the neighboring hybrids gives us an attacker that distinguishes the KEM candidate.

This is how section 6 supports section 5. We bound one replacement using the advantage of an explicit KEM attacker. We repeat the argument for each epoch, then add the bounds in section 7.

Why ideal receiving comes first.

The reduction does not know the secret key belonging to pk*. A real receiver can need that secret to decapsulate c*. The ideal receiver from section 5 instead obtains its shared key from the sender’s recorded table. This lets the reduction answer receives without knowing the target secret.

Thus, ideal receiving prepares the conversation for the reduction. KEM security then bounds the cost of replacing a challenge answer. Both parts are needed for the middle arrow.

Get the puzzle first. Then simulate.

The KEM interface first supplies pk*, then supplies c* and k*. Our reduction saves pk* in the first phase. After it receives the pair, it runs the entire SCKA attacker. It uses each sample only at the corresponding protocol event.

Proof detail: justify drawing the puzzle samples early

The reduction receives target samples before an honest protocol run draws them. We must prove that earlier sampling preserves the relevant distribution. Before target public-key generation, the simulator must not inspect pk*. Before target encapsulation, it must not inspect c* or k*.

If a target event never happens, its unused sample must have no effect. Eager/lazy sampling equivalence means earlier draws leave observations unchanged. The proof must preserve the joint distribution of key generation and encapsulation, including the ciphertext’s dependence on the public key.

Proof detail: handle the unknown secret and target exposure

The existing protocol state expects a secret at the target entry. The reduction samples an independent key pair and puts its secret there as a dummy. Ideal receiving checks that the entry exists, then reads the shared key from the sender’s table.

The dummy cannot replace the actual secret in a reply to corruption. Before the target challenge, an accepted exposure of target secrets or relevant coins stops the reduction. We must prove that these stopped paths contribute equally to the two neighboring games, so their difference cancels. After a target challenge, a conflicting exposure must receive the ordinary rejection. After erasure, permitted corruption can reveal the actual remaining state.

A rejected protocol query returns none and the conversation continues. A reduction abort ends its simulation and returns a fixed final bit. The proof uses optionRun and stopped-gap lemmas to keep these cases separate.

Proof detail: track both hidden differences together

The reduction’s random branch can differ from the honest-table hybrid in two places: the dummy secret and the candidate in the target’s table. A relation specifies which pairs of states we compare. We use one joint relation, called TargetRel in the plan, to track both differences.

The real KEM branch needs the secret difference. The random branch needs both differences. The internal correctness flag can also differ. Table entries must exist at the same epochs, and non-target data and exposure records must agree.

The relation must cover the period before receipt, the receiver’s copy of the key, erasure, and challenge attempts. Whenever both parties record the target key, they must agree within that execution. We must also couple the earlier random candidate to the hybrid’s fresh random target challenge answer. The sampling proof must justify using the same uniform value at those different times.

For every oracle query that continues the simulation, we must prove equal replies and preservation of the relation. A general simulation lemma then extends this result to the whole conversation. Accepted target exposures use the separate stopping and cancellation argument. Rejected exposures must still give identical rejections.

Challenge-answer hybrids let us reuse the existing invariant, a property preserved by every honest game step. That invariant requires recorded keys from supported KEM samples. A random table key generally fails it. We therefore relate the reduction to the honest hybrid instead of asserting that both satisfy the same invariant. This choice still requires the joint relation and its per-query preservation proof.

The local CKA-from-KEM security proof supplies patterns for hidden-state relations and sampling. We must adapt them to SCKA’s exposure rules.

Why IND-CPA rather than IND-CCA?

The network interface only delivers honestly recorded messages. Ideal receives avoid target decapsulation. With the simulation and exposure arguments proved, the reduction needs only the ordinary KEM challenge. It does not need a decryption oracle. This conclusion depends on the actual authentic-message game.

07 / KEEP THE UNITS STRAIGHT

Every term should have a reason.

Write δt for the KEM advantage of the explicit reduction for epoch t, measured as the distance between its real and random branches. The pinned KEM API calls this normalized guessing advantage. The SCKA API uses half that scale.

DSCKA ≤ 2q εcor + ∑t=0…2q δt
AdvSCKA ≤ q εcor + ½ ∑t=0…2q δtEpoch 0 has no key; choose its reduction to return a constant, so δ0 = 0. If every positive-epoch reduction has advantage at most δ, the uniform bound is q εcor + qδ. The endpoint, epoch-bound and reduction lemmas remain to be proved.

The earlier slot-based proposal had (q/2)δ. Epoch indexing gives a looser bound with fewer state and simulation obligations. The factor ½ in advantage normalization has not changed.

08 / THE FORMALIZATION

Use the machinery we already have.

VCVio represents a probabilistic oracle program with OracleComp. A QueryImpl defines the replies to its requests. simulateQ runs the program with those handlers; StateT carries the game’s state. Probability semantics give these programs a mathematical distribution.

Two VCVio examples are useful teachers. The one-time pad proof shows exact equality of distributions. The ElGamal proof defines a reduction, identifies its branches and derives a many-query bound. Their games differ from ours; we reuse the proof patterns and suitable APIs.

Other VCVio projects provide narrower lessons. aeneas-vcvio-demos illustrates ratchet-chain hybrids, cost accounting and a synthetic corruption-aware KEM protocol. signature-security-lean separates game definitions, theorem statements, reductions and assumption checks. Their repositories were inspected as references, not independently built or certified here. Neither supplies the missing Opp-BiKEM reduction.

What does Lean certify?

The kernel checks that a theorem follows from its definitions and assumptions. We must still review that those definitions match the intended threat model, that assumptions are meaningful, and that the result actually covers the advertised experiment. A successful build with an admitted theorem is not a completed security proof.

09 / THE WORKING ROUTE

Small tasks, explicit exit criteria.

The internal roadmap has the detailed contracts and source locations. Select a stage to see its purpose. Only the first implementation task is fully bounded by this iteration; each later milestone needs its own reviewed plan.

First bounded task

Security interface and coin marginals

Name the concrete oracle interface, adversary type and all-send budget. Prove that discarding the extra coins from a leaking send gives exactly the ordinary send computation.

Exit: four public declarations, both roles covered by one marginal theorem, full build and axiom checks; no new admissions.

Stages: interface and coin marginals → reviewed exposure policy and security invariants → both endpoint bounds → ideal invariants and target-key observation → eager per-epoch reductions and finite hybrid → final theorem, normalization and trust audit.

The remaining proof work: establish the ideal invariant, count epochs, justify sample timing, relate the dummy-secret state and prove that accepted exposure paths cancel. Underlying sends succeeding does not by itself prove that a leaking-send eligibility check always accepts. We keep those separate obligations explicit.

A final concrete theorem should assume only the declared protocol/KEM hypotheses and advantages of the explicit reductions. A later theorem about efficient adversaries needs resource-preservation evidence. Quantum security needs an appropriate quantum adversary model. The current classical oracle programs alone do not establish either claim, nor do they verify Rust or a deployed messaging application.

Check your understanding

Does erasure undo an earlier compromise? No. Exposure is permanent in the game.

Does an ideal receive prove secrecy? No. It prepares a later KEM reduction and has a correctness-error cost.

Why can’t we reveal a dummy target secret key? A corruption returns an actual protocol state; the distribution must be justified.

Why divide the branch-distance bound by two? The existing SCKA advantage measures deviation from ½, while the pinned KEM advantage is normalized to a full branch distance.
